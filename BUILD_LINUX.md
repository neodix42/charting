# Ubuntu development, build, and release

## Baseline and environment discovery

Target Ubuntu desktop, x86_64 first. Support the user's installed Ubuntu release; check
`/etc/os-release`, `uname -m`, and the read-only preflight script rather than assuming 22.04
or a fixed toolchain. Ubuntu 24.04 and 26.04 are target environments to test, not verified
compatibility claims in this instruction bundle. Record the actual tested distribution,
GTK/WebKit versions, display session (Wayland/X11), and GPU information in the delivery report.

Use Wails v2 and pin its CLI and Go module to compatible exact releases. Select a supported
Go toolchain and Node LTS compatible with the chosen frontend build dependencies; record
actual versions and commit go.mod/go.sum/package-lock.json. Avoid unbounded `@latest` in
release scripts. Do not add a speculative Go version that the user's installed toolchain
cannot parse. Generated Wails bindings and embedded frontend build assets must be included
in or reproducibly generated by the build process.

## System prerequisites

Wails' installation guide documents GTK3, WebKitGTK and compiler prerequisites. On Ubuntu
releases without the old WebKit 4.0 development package, its documented path uses WebKit 4.1
and the `webkit2_41` build tag. [S01]

After checking packages and obtaining permission for system changes, a typical 4.1 setup is:

```bash
sudo apt update
sudo apt install build-essential pkg-config libgtk-3-dev libwebkit2gtk-4.1-dev
```

This is an example, not a command to run automatically. Check package availability on the
actual release. Never add an obsolete PPA, downgrade desktop libraries, disable OS sandboxing,
or run the application as root to make it start. Missing GUI dependencies do not prevent
implementing/testing independent Go packages and frontend logic.

Common build shape once the project exists and pinned tooling is installed:

```bash
wails doctor
wails dev -tags webkit2_41
wails build -tags webkit2_41
```

Check the selected CLI's `--help` for exact supported flags. Apply the same WebKit tag to
Go tests/builds that compile GUI packages. Pure backend package tests should not import the
GUI and should run without GTK. Choose build tags consistently in scripts and CI. [S01]

## Required scripts Codex must implement

`scripts/dev.sh`, `scripts/build-linux.sh`, `scripts/test.sh`, and a user-local launcher/install
helper. Each script uses strict shell error handling, resolves the app root safely, prints
needed prerequisites, and exits nonzero on failure. Do not hide build failures with `|| true`.
Default install targets must be user-local and must not auto-start, auto-update or require sudo.
Provide dry-run behavior for the install helper and protect existing configuration.

The test script runs appropriate Go tests (race-enabled where supported), frontend typecheck,
lint, unit tests and production frontend build. GUI E2E tests can be a documented separate
step with a clear skip reason when no display/browser dependencies are available. Do not
force optional live exchange smoke tests into deterministic CI.

## Release deliverables

Ship source, a release binary, `.desktop` launcher, app icon created for this project,
third-party notices, version manifest, checksums, and exact build instructions. The app must
start without `wails dev`, Vite, npm or a development server running. Linux shared libraries
still need to exist; do not call the binary fully static or portable to every distribution.

A tar.gz user-local distribution is sufficient for v1. A tested .deb is desirable but must
not delay a working app. AppImage is optional, not required: bundling GTK/WebKit and licensing
properly is separate work. Build against the oldest supported runtime when appropriate, and
verify artifacts on the claimed target releases rather than assuming ABI compatibility.

## GUI verification

Test the actual Wails desktop webview, not just a Chromium dev preview. Confirm canvas
rendering, resize, keyboard shortcuts, native dialogs, copy/paste, attribution links and
shutdown persistence. Verify at normal and high DPI when available. Report Wayland window
position limitations honestly; size/maximized state are required, exact position is best
effort. If the environment has no display, provide exact user commands and mark GUI tests
unrun. Do not report a screenshot-free headless build as a successful manual desktop test.
