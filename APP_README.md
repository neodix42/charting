# CryptoDesk

CryptoDesk is an Ubuntu and Windows desktop chart workspace for crypto spot/perpetual and forex markets built with Go, Wails v2, React/TypeScript, Lightweight Charts v5, and SQLite. Binance, Bybit and Coinbase use public feeds without API keys or accounts. The DucasCopy forex source uses your Dukascopy JForex Demo/Live credentials and the included Java bridge. Releases run without a development server.

Open the symbol dropdown to browse both **Spot** and **Perpetual** instruments on Binance and Bybit. Each row shows its market type on the right; identical names such as BTCUSDT remain separate choices. The chart keeps the selected market on save/restart and uses its own historical/live feed and candle cache. Binance USD-M/COIN-M and Bybit linear/inverse perpetuals are supported, including XAGUSDT silver contracts. Dated futures and options are excluded. Coinbase currently supplies spot instruments. Search by symbol, base/quote asset or market label. If a provider category is restricted, available symbols remain usable alongside an explicit warning and Retry discovery.

**First launch has exactly one tab and one chart in a 1×1 grid.** Add tabs and charts as needed, up to 20 tabs and 9 charts per tab. Selecting a larger grid adds empty controls, not chart configurations. New tabs start with one chart. Later launches restore your actual saved workspace.

The original specification bundle is retained at the repository root. [STATUS.md](STATUS.md) describes observed verification and remaining limits.

## Run the built release

Run the root `./cryptodesk` produced by `./build.sh`, or extract `cryptodesk-X.Y.Z-linux-amd64.tar.gz` and run `./cryptodesk` inside its directory. This small archive requires compatible GTK3, WebKitGTK 4.1, libsoup3 and Linux desktop runtime libraries. Tested local build environment: Ubuntu 26.04.1 x86_64, Wayland, GTK 3.24.52, WebKitGTK 2.52.6.

On Ubuntu Desktop **24.04 or 26.04 x64**, install the system runtime dependencies once:

```bash
sudo apt update
sudo apt install -y \
  libgtk-3-0t64 libwebkit2gtk-4.1-0 libsoup-3.0-0 \
  glib-networking gsettings-desktop-schemas dconf-gsettings-backend \
  ca-certificates fonts-dejavu-core \
  libnss3 libnspr4 libasound2t64 libxss1
```

GTK3 provides the desktop window, WebKitGTK the embedded interface/JavaScript engine, and libsoup3 plus GLib networking the webview's HTTP/TLS support. NSS/NSPR, ALSA and X11 support libraries serve the private Screener Chromium. APT installs transitive dependencies automatically; the [Ubuntu package catalog](https://packages.ubuntu.com/noble/amd64/libwebkit2gtk-4.1-0) lists the WebKitGTK runtime dependencies. Keep the supplied `screener-runtime` folder beside the application: Node, dukascopy-node, trading-signals and Chromium are already included.

For **DucasCopy forex charts**, also install **Java 17 or newer** and keep the supplied `jforex-runtime` folder beside the executable:

```bash
sudo apt install -y openjdk-17-jre-headless
java -version
```

A JRE is sufficient to run forex charts; building the bridge needs a JDK. On Windows, install [Eclipse Temurin 17 x64](https://adoptium.net/temurin/releases/?version=17&os=windows&arch=x64) or another compatible Java runtime. CryptoDesk discovers `JAVA_HOME/bin/java` first, then `java` on `PATH`; restart the app after changing Java. The JForex desktop platform is not required. Crypto charts, Screener and Predictions do not require Java.

Use a graphical desktop session with working graphics drivers. GitHub releases build on Ubuntu 24.04; locally built archives require a glibc version compatible with their build host. Workspace storage remains in the normal user profile unless `--data-dir` is supplied. The separate Linux archive with bundled GTK/WebKit has been retired.

Optional user-local installation for the **Linux archive**:

```bash
./install-user.sh --dry-run
./install-user.sh
```

This writes the app under `$XDG_DATA_HOME/cryptodesk-app` (normally `~/.local/share/cryptodesk-app`), registers its application launcher and installs the same diamond logo shown in the app's top-left corner. The launcher uses an absolute PNG icon path, with SVG and eight PNG sizes also registered in the user icon theme. The native window embeds a smaller copy that GTK accepts on X11; the matching `cryptodesk` desktop identity provides Wayland taskbar association. Windows builds carry the same logo in their executable resources.

If your configured desktop folder exists, installation also creates an executable `cryptodesk.desktop` shortcut there, preserving any differing existing shortcut. It sets that file's trusted metadata when supported; your desktop may still require **Allow Launching**. Per-user icon/application metadata is refreshed when the desktop tools are available. No system settings or workspace data are changed. The installer copies the complete private Screener runtime and the five-file JForex bridge, validating its inventory before installation and restoring the previous bridge if installation fails. The original extraction folder can then be removed.

Run the installer again after rebuilding or downloading an updated archive, then close and reopen CryptoDesk. If an existing pinned taskbar entry retains an old icon, unpin it and pin the newly installed **CryptoDesk** application entry. Installation does not start the app. Source-checkout equivalent: `scripts/install-user.sh --dry-run` after building.

## Downloads and release versions

The main [README](https://github.com/neodix42/charting#download) links to the [latest release](https://github.com/neodix42/charting/releases/latest). Pushing commits to `main` runs the [release workflow](.github/workflows/release.yml): build the standard Linux archive and Windows ZIP, assign `v0.1.0` initially and increment subsequent patch tags, verify package contents, architecture, version and provenance, then publish both versioned packages together. Test suites run separately and do not gate publication. `SHA256SUMS` verifies the archives and `release.json` records their version, source commit and hashes. Historical completed releases, including older bundled Linux downloads, remain preserved and checksum-verified. The workflow assumes `main` is the default branch. Superseded queued commits or older workflow contents are skipped in favor of the newer push; a workflow change during a build stops publication before remote writes.

The header displays the installed build's `vX.Y.Z` release tag beside the CryptoDesk name. It is embedded at build time and works offline; it does not change when a newer release is published. Packaging verifies that the UI version matches the selected release, and diagnostics reports the same compiled version.

Local builds use the baseline in `VERSION` (currently `0.1.0`). Set `CRYPTODESK_VERSION=X.Y.Z` to override it for either build script; the header, output filename, package manifest and Windows product version follow this value. Release CI passes its selected version without making source-version bump commits. Hosted execution and Windows GUI checks are recorded separately in [STATUS.md](STATUS.md).

The independent [Tests workflow](.github/workflows/tests.yml) runs on `main` pushes, pull requests and manual dispatch. It runs all automated suites, including browser interactions and offline verification of the packaged Screener enrichment/Refresh runtime. Its artifacts are **diagnostics-runtime-linux-amd64** for runtime reports and **diagnostics-browser-linux-amd64** for browser reports and failure screenshots/traces; diagnostics are retained on success or failure. A test failure does not stop the release workflow. The retired GTK/WebKit bundle's namespace provisioning, runtime redistribution and source collection no longer run.

## Build and develop

Pinned versions: Go module/CLI Wails 2.17.0; React 19.3.1; Lightweight Charts 5.2.1; SQLite Go driver modernc.org/sqlite 1.60.1. This checkout was built with Go 1.26.8, Node 24.19.0 and npm 11.17.0. Frontend and Go lockfiles are included.

Install Go, Python 3.12+, **JDK 17+** with `java` and `javac`, a C compiler and pkg-config. On Ubuntu, `sudo apt install openjdk-17-jdk-headless` supplies the Java build tools. Build/dev/test scripts check that both Node and npm run. If either is missing or incompatible, they download the official Node 24.19.0 bundle (including npm), verify its pinned SHA-256, and reuse it under `.tools/` on later runs. The selected `bin` directory is exported to Wails and its child processes. No shell-profile edits, global npm installation or IDE runtime paths are needed. Initial download requires access to `nodejs.org`; alternatively provide Node 24 LTS with npm on your terminal's PATH.

Linux native builds also require GTK3 and WebKitGTK 4.1 development packages; the standard Ubuntu package names are `libgtk-3-dev` and `libwebkit2gtk-4.1-dev`. Installing OS packages is a separate user/admin action.

On an Ubuntu machine which already has the corresponding runtime libraries, `scripts/bootstrap-native-sdk.sh` is an optional unprivileged alternative: it downloads exact currently resolved Ubuntu development-package archives and extracts them under ignored `.tools/native`; it does not install packages or change the OS. `scripts/native-env.sh` scopes those headers/linker paths to the invoking process. This SDK path was used in the test environment. Repositories/network access are needed for bootstrap; package versions are recorded in `.tools/native/package-versions.txt`.

```bash
./build.sh                   # ready-to-run app + standard Linux archive + checksums in repo root
./win-build.sh               # cross-build Windows x64 ZIP with English WebView2 locale packs
scripts/build-linux.sh       # pinned local CLI, production frontend + desktop + archive
scripts/dev.sh               # desktop development
scripts/test.sh              # deterministic Go race/vet + frontend checks/build
cd frontend && npm run test:e2e
```

`./build.sh` works from any current directory and publishes `cryptodesk`, its sibling `jforex-runtime` folder, `cryptodesk-X.Y.Z-linux-amd64.tar.gz`, and `cryptodesk-SHA256SUMS` at the repository root. Launch `./cryptodesk`, or copy the complete archive to a compatible Linux desktop, extract it and launch the included executable. Verify root outputs with `sha256sum -c cryptodesk-SHA256SUMS`.

Both Linux and Windows builds compile our JForex bridge with Java 17 bytecode, using checksum-pinned SDK **3.6.51 / API 2.13.99** artifacts from Dukascopy's official Maven repository and Maven Central. The approximately **43 MB** SDK build cache lives under `.tools/jforex-sdk/cache`; vendor SDK JARs are excluded from release archives. Each package contains only `cryptodesk-jforex.jar`, `SDK-ARTIFACTS.json`, `JFOREX-PROVENANCE.json`, `LICENSE` and `THIRD_PARTY_NOTICES.md` inside `jforex-runtime`. Package validation checks all five files, their hashes and matching `version.json` provenance.

For source-checkout development before a full build, run `python3 scripts/jforex_bundle.py --output jforex-runtime`. `python3 scripts/jforex_bundle.py --test` verifies the bridge and actual SDK bootstrap without account credentials; initial SDK downloads still need network access. `CRYPTODESK_JFOREX_RUNTIME` can explicitly select another complete bridge folder. This is independent of the Screener runtime override.

Binding generation runs without opening a workspace database, so building while CryptoDesk is open does not conflict with its workspace lock.

`./build.sh` checks for a newer stable `dukascopy-node` release before compilation and adopts it only after staged compatibility checks and offline runtime tests pass. Set `CRYPTODESK_UPDATE_SCREENER=0` to keep the current exact pin; release CI does this for consistent Linux/Windows packages. See [Updating the Screener downloader](README.md#updating-the-screener-downloader) for update behavior, bundled-version checks and installation instructions.

For Windows, run `./win-build.sh` on Ubuntu with Go, Python 3.12+, **JDK 17+** and `7z` (Ubuntu package `7zip`). It produces `cryptodesk-X.Y.Z-windows-amd64.zip` and `cryptodesk-Windows-SHA256SUMS` in the root. The ZIP includes Microsoft Fixed Version WebView2 with English (`en-US` and `en-GB`) locale packs; other locale PAKs are omitted. The complete source runtime is verified against its pinned version, SHA-256 and inventory before reducing only the staged package. Shared resources and all licenses are retained. Build sources are copied to a temporary directory, preserving existing generated bindings, uncommitted files and Linux outputs. The script uses project-local Node/npm/Wails and does not install system packages. Fresh machines download the pinned Windows-only Go WebView2 module before preparing the English-language overlay; a prefilled Go module cache is not required, and normal Go checksum/source verification remains enabled. Initial runtime download is about 300 MB; the complete verified runtime remains cached under `.tools/webview2`. Use `./win-build.sh --webview2-cab /path/to/pinned.cab` for a local copy of the exact pinned runtime.

On Windows, extract the **whole ZIP** to a local writable folder and launch `cryptodesk.exe`. Keep `WebView2`, `screener-runtime`, `jforex-runtime` and `portable.marker` beside it; the workspace and browser profile live in its `data` directory. This needs no separate WebView2 installation; forex charts additionally need the separately installed Java runtime. Windows 10 startup applies Microsoft's required read/execute grants to the bundled runtime directory; Windows 11 needs no grants. Fixed runtime updates require a new reviewed runtime pin and rebuild. The executable is unsigned, and cross-compilation on Ubuntu does not replace Windows runtime testing. Full details: [Windows portable build and usage](docs/WINDOWS_PORTABLE.md).

The underlying `scripts/build-linux.sh` also retains `build/bin/cryptodesk` and the distribution under `release/`, including checksums, licenses and a version manifest. Build scripts never use sudo or a system package installation. The CLI is installed into project-local `.tools/` if absent. Normal builds contain local assets and no fixture bridge.

Optional live and native verification:

```bash
go run ./cmd/smoke -duration 65s
scripts/smoke-desktop.sh
```

Live smoke makes public requests and reports exact outcomes. Native smoke uses an isolated temporary workspace and an explicitly tagged automation binary, real public feeds and the actual Wails/WebKit webview. Browser E2E uses a separately labelled explicit test bridge; it is not a live-exchange or desktop test.

## Use

Use the **＋** immediately after the tabs, or Ctrl+T, to create a single-chart tab; Add Chart or Ctrl+Shift+N adds one chart. The tabs and **＋** share one horizontally scrolling strip, so scroll along the row to reach later tabs. Ctrl+Tab / Ctrl+Shift+Tab changes tab; Ctrl+W closes the active tab with confirmation. **Double-click a tab to rename it. Middle-click any tab** to close that tab and all its charts without a confirmation dialog; an inactive target stays inactive. The final tab cannot be closed. Each chart has a larger **×** button that removes the chart immediately without confirmation; the final chart in a tab stays protected. Shortcuts stay inactive in editors/selectors. Duplicate a tab from the header or drag tabs to reorder; drag chart headers to reorder charts. Row/column splitters resize tracks. Maximize chart temporarily and restore it without changing the saved grid.

Each chart has its own exchange, searchable native instrument, horizontal period buttons (`1m`, `5m`, `15m`, `1h`, `4h`, `1d`, `1w`), volume, candlestick/line style and linear/log scale. The buttons stay in the chart header row; small chart headers scroll horizontally. Drag/pan/zoom the chart; scrolling left loads older history. Return to live follows current bars. Manual price scaling and time viewports are saved. Settings provides theme, IANA/system timezone, optional local candle storage, JSON import/export/reset and diagnostics. Candle boundaries remain UTC regardless of display timezone.

**Settings → Chart right gap** sets the space between the latest candle and the chart’s right edge for every tab. Choose **Bars** (default **10**) or **Pixels**, enter a whole number, and press **Apply**. All current charts update immediately, including maximized siblings; inactive tabs use the same setting when opened. Changing the gap returns all charts to live while retaining their zoom and price settings. The preference survives restart and JSON export/import. Accepted values are 0–500 bars or 0–5,000 CSS pixels; a gap that exceeds the available chart width is reduced to keep the latest candle visible. Ichimoku’s projected cloud does not move the gap’s anchor away from the latest price candle.

Centered in the top header alongside the CryptoDesk logo, shared period buttons and an **Indicators** dropdown apply to every existing chart in the current tab, including charts hidden by maximization. Grid, Add chart and Duplicate controls sit to their right, immediately before the save indicator. Its width stays fixed while changes are pending, saving, saved or awaiting retry, keeping neighboring controls in place. Narrow windows use compact action icons with tooltips. Tab names remain in the tab row. A period click updates all those charts immediately and returns them to live view. The shared period is highlighted only when every chart agrees; individual chart controls can still override it. For an indicator, configure its parameters once and press **OK** to add an independent instance to every chart in the tab. Existing indicators are retained, other tabs stay unchanged, and all changes are saved. If any chart already has 12 indicators, the shared dropdown is disabled until an indicator is removed from that chart.

Weekly candles start Monday at 00:00 UTC. Binance, Bybit and DucasCopy provide native weekly candles. Coinbase weekly history is derived from actual daily candles, with live updates from its public trades; incomplete weekly coverage remains provisional.

### Drawing tools

Every chart has a **Draw** toolbar: **Arrow up**, **Arrow down**, **Horizontal line** and **Trendline**. Choose a tool, then click the price chart to place it. A trendline uses two clicks, one for each end, with a preview between them. Press **Esc** or choose **Cursor** to cancel an unfinished drawing and resume panning. **Undo drawing** removes the last drawing on the current instrument; **Clear drawings** removes all drawings on that instrument.

**Single-click a drawing to select it.** Select an arrow by its tip or shaft, a horizontal line anywhere along it, or a trendline along its segment. Click **Delete** in that chart's toolbar or press **Delete / Del** to remove the selected item. Keyboard deletion is suspended while typing or using a dialog. Clicking empty chart space or pressing **Esc** clears the selection.

Selected lines show square handles. **Drag either endpoint and release** to change its position or length. A full-width horizontal line becomes a finite horizontal segment when an endpoint is dragged; it stays horizontal as you adjust either end. **Esc** or **Cursor** cancels an unfinished adjustment. Changes are saved after release.

To reposition a whole item, **double-click the drawing**, move the pointer, then **click to place it**. Trendlines and finite horizontal segments keep their shape and the point where you grabbed them. **Esc**, **Cursor** or a chart header control cancels the move and keeps the previous position. Clicking **Save** during a move or endpoint adjustment saves the previous completed position and keeps the preview active. Completed edits retain the drawing's identity, and both edits and deletions restore after restart.

Completed drawings autosave to SQLite and restore after restart, tab switches and JSON export/import. Positions use UTC times and prices, so zooming, resizing and changing timeframes preserve their anchors. Drawings belong to their chart, exchange, market and instrument: switching symbols hides unrelated drawings and switching back restores them. Add Chart starts without drawings; Duplicate Tab copies them independently. Each chart supports up to 100 saved drawings across its instruments.

### Indicators

Each chart has an **Indicators** dropdown. Select SMA, EMA, Ichimoku Cloud or MACD, adjust its parameters, then press **OK** to add it. SMA and EMA also offer **Line width** from **1–4 px**, default **2 px**, in both individual and shared dialogs. Cancel leaves the chart unchanged. Click an applied indicator's label to edit it, or its × to remove it. Multiple instances can use different periods, colors and line widths; settings are independent per chart and survive restart and JSON export/import. There are at most 12 indicators per chart to bound rendering work. Existing SMA/EMA instances without a width retain their two-pixel appearance.

| Indicator | Default parameters | Display |
|---|---|---|
| SMA | Close-price period 20, line width 2 px | Price overlay |
| EMA | Close-price period 20, line width 2 px | Price overlay |
| Ichimoku Cloud | Conversion 9, base 26, leading span B 52, displacement 26 | Conversion/base/leading/lagging lines and green/red cloud between the leading spans |
| MACD | Fast 12, slow 26, signal 9 | Separate pane with MACD/signal lines, histogram and zero baseline |

Drag the separator above a MACD pane to resize it. Each MACD instance saves its own height relative to the main price pane, restoring the same proportions after tab switches, parameter edits, restart and JSON export/import. The proportions adapt when the chart or window is resized.

Periods count chart candles, from 1 to 2,000; Ichimoku displacement is 0–500 bars. MACD fast must be smaller than slow. Color controls the indicator's primary line. Long periods request older candles automatically, with a visible warm-up/history status when available data is insufficient. Calculations use the loaded candle window, including the current provisional candle, and update after candle corrections. EMA seeds from a full SMA window before applying `2 / (period + 1)`; MACD's signal uses the same EMA convention. Ichimoku displaces leading spans forward and the close backward by the configured number of bars, extrapolating future timestamps only for the projected cloud. The cloud contains derived values, never invented future prices. Earlier history can change an EMA's seed, so results can differ slightly from chart services with a different seed/history window.

Existing workspaces without an `indicators` field continue to load unchanged. Indicator calculations are local; no additional account, data feed or subscription is required. Indicator changes reuse the existing chart and feed.

Only the active tab mounts charts and requests leases. Identical feeds share data and provider sockets; hidden tab leases release after a cancellable two-second grace. Cached data and chart settings remain. A larger grid never creates hidden subscriptions.

Live status and public-data details stay in the chart’s bottom-left footer, including when the cursor is over blank space or a future cloud span. Connection progress and feed failures retain their visible messages and retry controls.

Provider failures remain visible in their chart. Retry or reselect without losing configuration. Prices are never synthesized as a fallback. Coinbase live intervals derive from deduplicated trades, rather than relabelling its five-minute candle channel. An initial/reconnected partial bucket has provisional volume: the last REST snapshot or explicitly observed-only trades, never REST plus all buffered trade volume. Public Coinbase aliased USDC products are labelled/rejected; choose the actual USD product explicitly.

## DucasCopy forex charts

### Connect JForex

1. Install **Java 17+** and retain the release's `jforex-runtime` folder beside the executable.
2. Open **Settings → Ducas Copy**. Choose **Demo** or **Live**, enter **JForex Username** and the masked **JForex Password**, then click **Save credentials** or **Test connection**. Test saves the current draft before checking connectivity. Opening Settings alone never logs in.
3. On the first connection, the app downloads the pinned JForex SDK and dependencies (51 files, approximately **43 MB**) into the private profile. Downloaded files are checked against their exact sizes and SHA-256 before loading. Completed files are reused after interruption. **Cancel test** stops a pending Test or PIN challenge; it preserves saved credentials and existing chart streams. Connection setup can take several minutes on a slow network.
4. Select **DucasCopy** in a chart's source dropdown. Open its instrument list to choose a **Forex** pair, such as EUR/USD, GBP/USD or USD/JPY. Search ignores case and supports symbols, base/quote currencies and the displayed pair name.

The list comes from the logged-in account's available instruments, filtered to fiat currency pairs. The pinned SDK recognizes **70** such pairs; your Demo/Live account can expose a smaller set. Crypto, metal and other CFD instruments are not included in this chart source. Instrument availability and the optional Live PIN flow follow the SDK's [IClient interface](https://www.dukascopy.com/client/javadoc3/com/dukascopy/api/system/IClient.html).

For a Live account requiring security verification, click **Load PIN challenge**, enter the displayed code in **JForex PIN**, then click **Test connection**. The code is transient: it is cleared after use, cancellation, an error or a credential change and is never saved. An account with an appropriately registered IP can test without a PIN. A new app session may require a fresh challenge. CryptoDesk uses the official SDK authentication flow; account permission or network errors remain visible.

### Prices, history and storage

All seven chart periods are supported: **1m, 5m, 15m, 1h, 4h, 1d and 1w**. Historical candles and live updates consistently use **Bid** prices. Native weekly candles start Monday at 00:00 UTC. Market closures remain gaps; no weekend or holiday bars are invented. **Quote** freshness, connection errors, reconnection and market-closed status appear in the chart footer. Volume is the SDK's native **quote volume in millions**, not centralized exchange trade volume.

The JForex bridge runs only for requested forex discovery/history/quotes. Inactive chart tabs release their subscriptions. These authenticated charts use their own SDK cache, scoped by environment and a hash of the username; they do not write to or reuse the optional public-crypto SQLite candle cache. They also do not modify Screener CSVs or change dukascopy-node's WAF/rate-limit handling.

| Profile location | Contents |
|---|---|
| `dukascopy-jforex.json` | Saved username, Demo/Live environment and password |
| `jforex-runtime/3.6.51/lib` | Verified SDK dependencies downloaded on first use |
| `jforex-cache/<environment>/<account-hash>` | SDK historical-data cache |
| `jforex-private` | Private Java preferences and SDK runtime files |

`<profile>` is normally `~/.local/share/cryptodesk` on Linux, the Windows portable `data` folder, or the directory selected with `--data-dir`. Credentials persist separately from workspace JSON/export/import/reset and diagnostics. The settings file uses **0600 permissions on POSIX systems** and stores the password **without application-level encryption**; the saved password is never returned to the webview. Leave Password blank to retain it for the same username/environment, or check **Remove saved password** and save. A new username or environment requires its password.

Before changing an existing identity, close its active forex charts or select another source; this prevents mixing account-specific history. First-time setup can recover charts selected before credentials were entered. Pending saves/tests finish before Settings closes or the app shuts down normally; use **Cancel test** to stop a lengthy check. Test does not place orders, and CryptoDesk has no trade-execution integration. Automated SDK/bridge and fixture checks do not establish successful Demo/Live account connectivity; no real-account login has yet been verified. See [STATUS.md](STATUS.md).

## Settings

The app starts with a light window and loading screen. New workspaces default to Light; existing workspaces restore their saved theme.

Settings has eight tab pages: **Appearance** (theme, global font size, timezone and chart spacing), **Storage** (public crypto chart-candle cache), **Screener** (CSV folder and worker count), **Predictions** (local model and folder), **Ducas Copy** (JForex credentials and connection test), **Telegram Bot** (alert token and recipient), **Export** (workspace export/import/reset), and **Debug** (resource/backend diagnostics). Use Left/Right arrows or Home/End to navigate the settings tabs with the keyboard.

**Appearance → Font size** scales text across the app, including chart period controls, chart and application status bars, Screener controls and chart canvas labels. Choose **10–24 px**, default **15 px**. It takes effect immediately and persists in workspace autosaves and JSON exports; older workspaces use the default.

**Telegram Bot** provides a masked **Telegram Bot API Token** and **Recipient** (`@username` or a positive private chat ID). Entering a recipient beginning with `@` looks up the bot name and displays the setup instruction: the recipient must open that bot in Telegram and press **Start**. Then click **Test**. Test first saves both fields, then sends one CryptoDesk test notification and shows success or a helpful error. **Save Telegram Bot settings** saves locally without sending a message. Clear either field and save to remove its setting; both fields survive restart. Automatic monitoring is enabled explicitly under **Screener → Live Alerts**; saving Telegram settings alone never starts it.

For `@username`, Test finds the recipient among up to 100 pending private-chat updates, verifies their current username and remembers their numeric chat ID for that bot. Later tests recheck the current chat identity, including after restart, without depending on old updates still being available. If the recipient cannot be found, send `/start` to the bot again or use their numeric private chat ID. Existing webhooks are preserved; use a numeric private chat ID when the bot is managed by a webhook. Lookup does not acknowledge/drop pending updates or alter update filters. Sends are never automatically retried; when delivery is uncertain, check Telegram before clicking Test again. [Telegram bot setup rules](https://core.telegram.org/bots#how-are-bots-different-from-users), [Bot API updates](https://core.telegram.org/bots/api#getupdates).

The token, recipient and verified chat identity are stored in `<profile>/telegram-bot.json`, separately from workspace JSON, backups, import/export/reset and diagnostics. Saved files use owner-only permissions on POSIX systems; the value is stored locally without application-level encryption. Pending saves finish before settings close or normal app shutdown. A failed save preserves the previous token and reports a generic error without displaying secret values. If a profile is kept inside the repository, the configuration and temporary token files are ignored by Git.

## Local candle storage

This optional SQLite cache serves public crypto chart feeds. DucasCopy uses its separate, account/environment-scoped SDK cache described above.

**Store candle data locally** in **Settings → Storage** is **off by default**. Check it, edit the **Storage folder** path or use **Choose folder…**, then click **Apply**. Checkbox and folder edits take effect together only when Apply succeeds. Clearing the path and applying selects the default folder. Failed configuration changes remain visible and preserve the previously applied setting; Apply can retry the same configuration after a storage error.

The default folder is `<profile>/candles`: normally `~/.local/share/cryptodesk/candles` on Linux, or `$XDG_DATA_HOME/cryptodesk/candles` when that variable is set. `--data-dir` selects the profile and therefore its default candle folder. The Windows portable profile uses `data/candles` beside the executable. The optional database is `candles.sqlite3` inside the selected folder. The enabled flag and chosen path are saved separately in `<profile>/candle-storage.json`; workspace JSON import, export and Reset Workspace do not change them or include cache contents.

Settings shows the applied folder and its total size. **Refresh** measures it again; while storage is enabled and its settings are visible, size updates approximately every five seconds. The total includes SQLite sidecars and other regular files in the selected folder; symlinks are not followed. Folder edits do not replace the applied path or its size until Apply succeeds.

Enabling storage saves genuine downloaded candles currently held in memory, then stores accepted live updates and history pages by exchange, instrument and period. On restart, saved candles can appear immediately with a **cached** status while real public data reconnects. Complete, contiguous pages of closed historical candles can be reused from disk. Current/open candles, missing coverage and gaps still require provider data; unavailable feeds remain visibly unavailable rather than being presented as live cached prices.

Disabling storage stops disk caching and leaves existing files intact. Changing folders opens the selected cache for subsequent storage without moving or deleting the previous folder; select the old folder again to reuse its data. Disk storage can grow with downloaded history and has no automatic eviction or deletion. Memory caches and active chart windows remain bounded.

## Screener

The fixed **Screener** tab stays at the right of the chart tabs, independently of the 20-chart-tab limit. Opening it saves the chart view and releases its chart subscriptions. Selecting a chart tab restores that workspace. **Analysis** evaluates visual rules against downloaded closed bars; **Enrichment** adds indicators and refreshes histories.

CryptoDesk pins **[dukascopy-node 1.51.1](https://github.com/Leo4815162342/dukascopy-node/releases/tag/v1.51.1)**, including the merged plain-403 fix and upstream export-widget request headers. The local runtime and release packages use the same exact version; parallel downloads retain existing pacing, cooldowns and checkpoints.

Open **Screener → Downloader** to browse the instruments supported by the bundled [dukascopy-node](https://github.com/Leo4815162342/dukascopy-node), grouped by its README categories. Search for an instrument, select individual instruments, a category, or all instruments, and choose one common timeframe and UTC date range. The start date is included and the end date is excluded. Press **Download** to queue CSV downloads; each instrument shows its progress, result or provider error. You can leave the Screener while downloads continue, or cancel the batch. Closing the app pauses unfinished downloads; they resume automatically on the next launch. Completed files are retained and completed jobs in that batch are not repeated on resume.

**Select all downloaded assets** replaces the current selection with supported symbols that have published CSV files in the configured folder. Multiple ranges/timeframes count once, and files from earlier sessions count independently of the current queue. Search and collapsed categories do not restrict this selection. Hidden partials, backups, directories, symlinks and removed files do not count. The selected symbols use the normal saved preferences.

**Download** matches existing CSVs by symbol and timeframe, independently of their filename dates, and publishes **one CSV for each symbol/timeframe**. It reuses local history and requests only uncovered parts of the selected From–To interval: an earlier From prepends data, a later To appends data, and gaps between separate saved ranges are fetched only when requested. Already covered intervals require no network requests. Narrowing the requested dates retains all saved rows. New assets/timeframes still get a new CSV.

When multiple saved files cover the same asset/timeframe, the downloader merges their local data and reuses their combined coverage. Overlapping candles prefer the source with the earliest filename start, then the latest end; candle timestamps remain unique and repeated ticks retain their multiplicities. The union of applied indicator columns is recalculated over the combined chronological history, including improved warm-up context from prepended data. Unknown derived columns fail visibly while preserving the sources.

The filename expands to the earliest requested/saved start and latest requested/saved end, also covering the actual first and last CSV timestamps. Its end date remains exclusive, so it is at least the UTC day after the last row. A narrower request never shrinks the name or truncates history. After the complete result and metadata are published, superseded CSVs and their metadata are removed from the main folder. Exact originals, previous metadata and a recovery journal remain in hidden `.cryptodesk-history-publications/<transaction>/` folders. Publication requires filesystem hard links; backups accumulate and are never deleted automatically. Existing older backup folders are retained. An unchanged single history with the same filename is not rewritten.

To is exclusive; selecting tomorrow UTC requests the latest available data through the batch's execution cutoff. Current partial candles remain eligible for another download until closed. Successful query coverage remembers closed intervals, including market closures and pre-listing periods with no rows. Older CSVs without a ledger reuse their actual saved span. Dukascopy source files can cover larger UTC time buckets than the requested missing range; existing covered rows are not appended again. **Enrichment → Refresh data and indicators** also revises recent source values and verifies histories whose coverage fingerprint is missing or changed.

Valid empty source intervals are skipped and downloading continues with later intervals. A completely empty new history reports that no rows are available. Refresh and updates retain existing rows and indicator columns when a newly queried interval has no candles. Malformed provider responses remain visible errors; empty intervals never create artificial candles.

**Downloads run in parallel**, with up to **5 active symbols by default**. **Settings → Screener → Worker threads** accepts **1–20**, applying the same saved limit to Downloader, Enrich and Refresh. Finish or cancel active work before changing the setting. Additional symbols wait for an available worker. The Downloads panel uses **10 jobs per page** and reports completed and failed counts. Use **Show downloads** to view Failed, Completed or other states; **All statuses** includes completed jobs. Status filtering happens before pagination and does not affect the running queue. Results stay in selection order, and each symbol has its own progress and error. Each worker fetches source files sequentially while different symbols can download concurrently. Cancel stops all active and queued downloads while retaining completed CSV files.

Symbol selection, timeframe, dates and each category's open/closed state are saved immediately and restored after restart. Worker threads is stored with the download folder in `<profile>/screener.json`; older profiles without it default to 5. Resumed downloads use this setting, independently of older queue or selection worker counts. Normal close waits for the last selection write. Failed saves remain visible and pause normal close until retried or explicitly discarded. These choices are machine-local and are independent of chart workspace imports and resets.

The download queue is stored in `<profile>/screener-downloads.json`, and UI choices in `<profile>/screener-view.json`. Each unfinished symbol has a private `.cryptodesk-screener-job-…` folder in its download destination. New histories have a CSV partial and committed source-batch checkpoint; updates also keep a source snapshot, missing-range plan and a checkpoint for each range. Keep these folders to resume work. Restart retains complete source batches and retries only uncommitted work, without duplicate CSV rows or publishing half an extension. Existing originals stay intact until all requested ranges and indicator calculations finish. **Cancel downloads** intentionally discards unfinished work and prevents automatic restart; **Resume downloads** retries paused/failed work from any retained checkpoint. Changed source files and invalid checkpoints fail visibly while preserving originals. Downloads, enrichment, refresh and Analysis serialize access to changing histories.

**Settings → Screener → Screener download folder** changes the destination for future downloads. The Linux default is `~/.local/share/cryptodesk/screener` (`/home/neodix/.local/share/cryptodesk/screener` for this checkout's user). It follows `$XDG_DATA_HOME` or an explicit `--data-dir` profile. Windows portable builds use `data/screener` beside the executable. Choosing or typing a path takes effect only after **Apply** succeeds. Changing folders does not move or remove previous downloads. The machine-local preference stays outside workspace import, export and reset.

Release archives include a private Node runtime, the pinned Dukascopy downloader and its browser support. Extract the complete archive and keep `screener-runtime` beside the application; no global Node/npm installation or runtime `npx` installation is needed. See [updating the Screener downloader](README.md#updating-the-screener-downloader) for version checks, restoring the pinned dependency and upgrading it from source. Downloads require network access to Dukascopy. Upstream restrictions and empty/unavailable ranges are reported as errors; chart data and synthetic fixtures are never substituted. Tick histories and selecting every instrument can produce substantial downloads.

Downloader and Refresh share the downloader library's browser-session cache at `<profile>/screener-provider/waf-token.json`. It is retained across files, batches and app restarts instead of being deleted with each CSV's scratch folder. The active request establishes or reuses the shared session; later symbols reuse it without launching concurrent browsers. Keep this machine-local session file private; it is unrelated to the downloaded market-data CSVs.

Downloader and Refresh share one Go-owned request queue through their existing private owner pipes. Request starts are at least **two seconds apart**, including requests from different file workers. Initial browser-session setup is shared; subsequent data requests can overlap up to the worker limit. Each worker fetches one source file at a time. This is a conservative application policy; no published quota for this endpoint was established. Status messages explain pacing and provider cooldown waits. Queue waiting does not consume the library's thirty-second network timeout. Cancel/close interrupts waiting immediately.

HTTP **429** pauses the shared queue using `Retry-After` (delta seconds or HTTP date) and exponential backoff of 5–60 seconds. The library retains its two bounded retries. Provider waits longer than five minutes stop automatic attempts instead of being shortened. The saved `<profile>/screener-provider/rate-limit.json` retains pacing and cooldown deadlines across batches/restart. If Dukascopy refuses access with **HTTP 403**, requests stop and a **15-minute access-denial cooldown** is saved, extended by any longer provider `Retry-After`. The error shows the next manual retry time. **Resume downloads** or **Refresh data and indicators** during that cooldown sends no request, and does not extend the deadline. Completed files, existing CSVs and resumable download checkpoints remain available. An ongoing 403 needs Dukascopy to restore/authorize access; reinstalling Node or CryptoDesk cannot guarantee this. Consult [Dukascopy support](https://www.dukascopy.bank/contact/) if it persists. CryptoDesk does not switch endpoints or substitute data after an access denial.

For an optional live desktop verification, run `scripts/smoke-screener.sh` after building the bundled runtime. It uses a temporary profile, explicitly selects one worker and downloads two BTCUSD and two ETHUSD daily candles through the actual download button. Set `CRYPTODESK_SCREENER_EVIDENCE` to choose the evidence folder; no user workspace is opened.

`scripts/smoke-screener-resume.sh` performs a real close/restart during two minute-history downloads. It verifies automatic continuation, identical job IDs, unchanged committed CSV prefixes, no duplicate files, ordered candles, and restored selections/category state in an isolated profile.

### Enrichment

Open **Screener → Enrichment** to list published CSV files in the configured Screener folder. The table shows filenames, timeframes, sizes, comma separated header fields and the **actual UTC timestamps of the first and last CSV rows**. Candle timestamps are bar open times; tick files show tick times. The period is read directly using bounded head/tail reads, including before the first refresh and after external appends. Filename dates and saved metadata do not override the actual period. Empty files or files without usable timestamps show **Period unavailable**, with malformed data reported. All files are accessible through **20-row pagination**, including earlier sessions' downloads; hidden partials, backups, directories and symlinks are excluded. **Reload file list** discovers newly completed downloads; completing a refresh reloads the updated period and fields automatically.

Choose an indicator and its parameters, then press **Enrich** to process all CSV files currently in that folder, including other pages. The bundled [trading-signals](https://github.com/bennycode/trading-signals) **8.3.0** integration supports **40 indicators**: twelve moving averages, RSI, MACD, ROC, momentum, AO, AC, CCI, stochastic oscillators, ADX/ADXR/DX, Ichimoku/Tenkan/Kijun, ATR, true range, Bollinger bands/bandwidth, Donchian channels, OBV, VWAP/VWMA, MFI, CMF, accumulation/distribution, price volume trend and force index.

The **Time** category also offers **Weekday** and **Hour**, calculated directly from each row’s timestamp in **UTC**. `weekday` is **1 for Monday through 7 for Sunday**; `hour` is **0 through 23**. These fields need only `timestamp` in Unix milliseconds, take no parameters or price source, and have no warm-up. They work with candle and tick files; candle timestamps identify the bar’s opening time. Refresh recalculates them for new and existing rows, and Analysis can compare them with constants or earlier values.

Columns have readable names such as `sma_200`, `tenkan_9`, `macd_12_26`, `macd_signal_12_26_9` and `macd_histogram_12_26_9`. All defining parameters distinguish configurations. Repeating a calculation replaces its matching columns without duplicates; original fields and other indicators are preserved. Periods count input rows. Warm-up and mathematically undefined results stay empty. The library's initialization conventions can differ from chart indicators. Ichimoku stores unshifted values on calculation rows, with independent line warm-ups and no future/displaced rows.

Price indicators default to **close**, then **bidPrice**, then **askPrice** for tick files. Choose another source explicitly when needed; non-close names include their source, such as `sma_200_bidprice`. Candle and volume indicators require the fields shown in the form. Tick data is not converted into artificial candles. Missing fields, invalid numbers, malformed CSV or descending timestamps fail that file visibly while other files continue. Original volume units are retained.

Local enrichment uses the **Settings → Screener → Worker threads** limit, default **5** parallel files and configurable from **1–20**, with overall and per-file progress and no provider requests. Before Enrich or Refresh processes a symbol/timeframe, it consolidates any legacy overlapping, subset or separate CSVs locally into one history, retaining every saved bar and replaying the combined applied indicators. This step makes no provider requests and leaves gaps uncovered for a later download. Superseded files leave the main folder only after successful publication, with originals and recovery metadata retained in `.cryptodesk-history-publications`. A later provider refusal, including HTTP 403, leaves the consolidated history available.

Each worker has its own scratch directory, output and backup; one file’s failure does not stop the others. Each successful indicator calculation also preserves the exact input in `.cryptodesk-enrichment-backups/<job-id>.csv`, with matching JSON identifying its filename and parameters, before atomically replacing the CSV. It requires filesystem hard links, as downloads do. Backups accumulate and are never deleted automatically. Cancel or normal app close stops unfinished enrichment and retains completed files, including completed consolidation. Columns persist after restart; unfinished enrichment is not resumed automatically. Run the indicator again to recalculate it. A forced termination may leave a hidden temporary enrichment folder; the published CSV remains the previous or the fully enriched file.

**Refresh data and indicators** updates every existing downloadable history, including files on other pages, with up to the configured number of parallel file workers. After local consolidation, each worker downloads its history and recalculates its applied indicators before taking another file. Source requests within each worker are sequential and share the Downloader pacing and cooldown rules across workers. It repairs missing history, merges new fully closed bars and revises overlapping source values, then recalculates every applied indicator with its saved parameters. Files without a trusted coverage fingerprint are checked from their earliest saved/requested start through the present; verified histories use a recent overlap and new data. Manually changed files are verified again. Existing derived columns must have recoverable recipes; an unknown column or custom filename produces a visible file error while preserving that original. Tick refresh preserves repeated ticks at the same millisecond. Progress reports added and updated rows; refreshed histories use the same `.cryptodesk-history-publications` backups and recovery journal as downloads. Cancelling or closing keeps completed changes and preserves the current history; press Refresh again to finish remaining work. Refresh requires downloads to finish or be cancelled. Enrichment, refresh and analysis serialize work on existing CSVs.

The download cutoff is captured when Refresh starts and applies to every file, including queued files. Each file finishes downloading before its merged rows are enriched. Existing history supplies warm-up and recursive state, so applied indicators are recalculated correctly for appended rows and revised source values. Newly appended candles must have closed by the cutoff; ticks use the precise cutoff. The UTC period updates to the newest timestamp actually stored, which may be earlier than execution time during market closures or when provider data is delayed. Refresh expands the filename's exclusive end to at least the day after its UTC execution date, preserving any wider saved range. Progress, completed download paths and the file list follow renamed histories.

The indicator library and streaming CSV parser are preinstalled in Ubuntu and Windows release archives. Local enrichment needs no network or global Node/npm installation. `scripts/smoke-screener-enrichment.sh` verifies native buttons, real Dukascopy downloads, SMA/Tenkan and calendar values, exact backups, progress and restart discovery in an isolated profile.

### Analysis

Open **Screener → Analysis** and build **Visual condition rows**. Each operand can be a number, price, OHLC/volume field or an enriched indicator. Field operands offer a timeframe, **Bars ago**, and an optional highest/lowest window. **+** adds a condition and **−** removes one. All rows must match together. Draft rules are remembered across app restarts independently of workspace export/import. Hover an operator or its **?** button for a description and example; keyboard users can focus the help button and press Escape to dismiss it.

**Period of data** selects **All periods**, **d1** or **h1** for the historical scan. It is retained with the draft and named conditions. A condition operand can still select another timeframe; its companion history remains available even when that timeframe is not the selected scan period.

Below **Apply conditions**, **Asset categories to scan** lists every Downloader category, all enabled by default. Toggle individual categories or use **Select all** / **Deselect all**. Only downloaded files in selected categories are scanned; selecting none disables Apply. Unrecognized/custom assets appear under **Other**. Scan categories survive draft saves and named-condition loading.

Press **Safe Condition** in the right-hand **Saved conditions** panel to name and save all current rows together. The list persists across restarts. Click an entry to replace the rows on the left with that saved snapshot, including operands, operators, timeframes, offsets and windows; press **Apply conditions** when ready to scan. Editing a loaded set changes the working draft. Saving under a new name keeps the original snapshot; duplicate names are rejected. Up to 100 named sets are stored in `<profile>/screener-saved-conditions.json`, separately from chart workspace import/export and the current analysis draft.

Right-click a saved condition and choose **Rename** to edit its prefilled name, or **Delete** to remove its named snapshot permanently. **Shift+F10** opens the same menu for the focused entry; arrow keys move between its actions. Renaming keeps the saved rows, categories, identity and list position. Names must contain 1–100 characters and be unique regardless of letter case. Both actions persist across restart and preserve the current editable rules and other saved entries; a failed operation shows an error and retains the saved entry.

Supported conditions are **Is above**, **Is below**, **Is equal**, **Crosses above**, **Crosses below**, **Is between**, **Is within a distance**, **Occurred within N bars**, **Remained true for N bars**, and **Highest/lowest in window**. Above/below are strict; between and distance include their boundaries. **Is equal** compares numeric values exactly without rounding or tolerance, for example `weekday` equal to `1` (Monday), `hour` equal to `0`, or Close equal to an earlier bar's Close. Use **Is within a distance** for approximate equality. Crosses compare the preceding and current closed bars. For distance, choose a multiplier and field or constant, for example Close within `0.2 × atr_14` of `sma_200`. Temporal conditions wrap another comparison, including **Is equal**, and count the evaluated file's closed bars. Highest/lowest compares the left value with the right operand's previous N values, excluding the current bar: Close greater than the previous 20-bar High is left Close, Highest in window, right High, 20 bars.

**Apply** scans downloaded files in the selected categories at every closed bar. Other timeframes use the same asset's latest fully closed data, without looking ahead; missing history, warm-up values and unavailable fields cannot produce a match. Required companion files must be downloaded and enriched first. Legitimate market closures remain usable through verified refresh coverage. Results show full catalog asset descriptions, matching assets/files, match counts and visible per-file errors. Matching assets uses **10 file records per page**; its **Asset category** filter applies before pagination without rerunning or changing the original scan scope. Analysis accepts up to 32 conditions, 10,000-bar lookbacks and 512 fields per CSV; files beyond these bounds report a visible error. Results are paginated without truncating occurrences. Completed files without matches are hidden while per-file failures remain visible.

**Simulate trade**, beside **Add condition**, adds optional **Stop Loss**, **Bars ago**, **Take profit** and **Duration** controls. Choose the Stop Loss field from the downloaded/enriched catalog. Its **Bars ago** defaults to **0**, using the matching bar's value; **1** uses the preceding bar's value. Whole offsets from **0–10,000** are supported, with unavailable earlier values counted as invalid levels. Take profit can use a matching-bar field or **1xSL**, **2xSL**, **3xSL**: `TP = entry + multiple × (entry − SL)`, calculated from the next bar's actual open. For example, entry 100 and SL 95 give TP 110 with 2xSL. Levels remain fixed after entry. Enter a whole **Duration** from **1–10,000 bars**. **Remove simulation** disables it; drafts and named conditions retain the settings across restart, load and rename.

After Apply, each match independently opens a simulated **long** trade at the next available closed bar's open. That entry bar is the first duration bar. A valid bracket requires `SL < entry < TP`. Missing levels or a next-bar opening gap outside that bracket count as invalid levels. Active trades resolve opening gaps before intrabar highs/lows; inclusive SL/TP touches count, with SL first when both are touched within one bar and order is unknown. Matches can overlap. A full duration without a hit expires; unresolved tail matches without enough closed bars count as insufficient future data. Missing required fields make simulation unavailable. Malformed CSVs retain the usual visible Analysis file errors. Tick data cannot supply candle-based simulation.

The additional **Profitable, %** result column is `100 × TP hits / all matches`, independently for each file/timeframe. Click its heading to sort highest first; click again for lowest first. Sorting uses the full, unrounded percentages across all category-filtered results before pagination. Pending or unavailable percentages stay last in either direction, and chart navigation follows the sorted order. Its expandable counts explain TP, SL, expiry, invalid levels, unavailable data and insufficient history. Every match remains in the denominator; no unreadable or unentered trade is silently discarded to improve the percentage. Fully unavailable simulations show an explicit unavailable label. This measures TP hit rate without position sizing, fees, slippage or monetary profit/loss. The result header retains the settings actually applied, even if you edit or remove the draft's simulation afterward; press Apply again to calculate new results. Existing match charts, category filtering and pagination continue to work.

Analysis is read-only: it does not consolidate or remove CSVs. Identical legacy datasets for the same symbol/timeframe are scanned and listed once, regardless of numeric formatting, column order or filename dates. Legacy files with differing ranges or indicator fields can still appear separately until the next **Refresh**, **Enrich** or **Download** consolidates that symbol/timeframe. Different timeframes remain separate. After consolidation, press Apply again to rebuild results against the single combined history.

Click a result to open its match chart. Candles (or tick price), available enriched series and any aligned timeframe values surround the highlighted match. With simulation enabled, **green dots below the original matching candles** identify visible matches whose trades hit TP, including exits outside the chart window. Other outcomes have no green dot. The selected match keeps its arrow. For a trade that opened, prices appear vertically as **Entry**, **SL**, then **TP**, beneath **Match** and in a text readout above the chart. **Entry** is the actual next-bar opening price used when the simulated trade opened. SL and TP are the fixed prices actually used by the applied simulation, including earlier-bar Stop Loss values and targets calculated from that entry price. Matches where no trade opened have no trade-price label. **Match Inspection** opens with bars three times wider than the fitted view and centers the selected match; zoom and pan still work. **Previous match** and **Next match** navigate occurrences, including adjacent result files. Reapply after changing data; stale charts are rejected. Results are temporary and rebuilt with Apply, while the rule draft persists. This analysis is historical and uses CSV row periods; it does not subscribe to live chart feeds.

`scripts/smoke-screener-analysis-refresh.sh` checks real desktop refresh, indicator replay, rule evaluation, chart navigation and restart restoration in an isolated profile.

## Predictions

The fixed **Predictions** tab sits immediately to the right of Screener. It forecasts **Close**, using downloaded Screener CSVs rather than live chart caches. Opening it saves chart viewports and releases live chart subscriptions; returning restores the selected chart tab. It does not count toward the twenty chart-tab limit.

1. Download the desired asset and candle period in **Screener → Downloader**. Use **Refresh data and indicators** first if newer actual data is needed. Predictions does not fetch provider data or modify the CSV.
2. Open **Predictions**. The first visit automatically prepares the selected model and an app-managed inference runtime. Progress shows the current download/setup phase and transferred bytes where available. **Start** stays disabled until both are ready. You can cancel, then explicitly retry; interrupted artifact downloads are retained for resuming. Opening Settings alone does not start a download.
3. Use **Filter assets** to narrow the asset dropdown by name or symbol; matching ignores letter case. Clearing the filter restores all downloaded assets. Filtering preserves the currently selected asset and period. Select an asset and one of its downloaded candle periods, then choose the latest **512 or 1024** fully closed bars. Tick files are excluded. At least that many valid closed rows must exist. The future horizon defaults to **20** and accepts **1–256** bars. These selections are remembered across restarts.
4. Click **Start**. The app reads ordered, finite Close values, excludes the still-open candle, checks the source for concurrent changes and runs the pinned Toto 2.0 model locally on CPU. Model loading and inference status remain visible. Cancel leaves saved snapshots and original CSVs intact.
5. Inspect historical Close, the median forecast and the shaded estimated **10th–90th percentile** band. Series names appear in the legend only, keeping chart labels uncluttered. You can pan and zoom. History retains real UTC timestamps; future bars are numbered **+1** through the requested horizon relative to the last observed closed bar. Future calendar timestamps are not invented, so weekends, session holidays and gaps do not produce misleading dates.
6. Select an earlier **saved forecast** to inspect it again. Each entry shows the model used for that run, alongside its asset, period, creation time and bar counts. Each immutable snapshot retains the input history and model output as they were at that run; refreshing actual data does not rewrite a past forecast.

### Model and storage settings

**Settings → Predictions** defaults to **[Datadog/Toto-2.0-313m](https://huggingface.co/Datadog/Toto-2.0-313m)**. The selector also offers the official 4m, 22m, 1B and 2.5B checkpoints. The default 313m weights occupy about **1.2 GB**; larger models require substantially more disk space and memory. CPU inference can take time, especially for larger checkpoints. The app uses the published `toto-2` package and a pinned CPU PyTorch runtime; it does not require a hosted model API, API key, GPU or global Python installation. [Upstream Toto documentation](https://github.com/DataDog/toto) describes the model family and its nine predicted quantiles.

The page shows the default and current **model storage folder**. On Linux the default is `~/.local/share/cryptodesk/predictions/models`; more generally it is `<profile>/predictions/models`, including `data/predictions/models` in the Windows portable profile. Choose another absolute folder and apply it before preparing the model. Changing the folder does not move or delete previous models. Settings cannot change while preparation or inference is active.

The private Python environment and pinned wheel cache live under `<profile>/predictions/runtime`, independently of the chosen model folder. Initial preparation needs internet access to the official Python release, package-wheel hosts and Hugging Face. Model repository revisions, download sizes and SHA-256 checksums are pinned; preparation validates artifacts before marking them ready, and inference rechecks its inputs. No model repository code is executed. Runtime setup and downloads stay within app-owned folders and do not change system packages or shell configuration. Linux and Windows x86-64 are supported.

Forecasts live in **`<profile>/predictions/forecasts`**, separately from Screener market data. JSON snapshots record the UTC creation time and input cutoff, symbol, description, period, lookback, horizon, model ID/revision, source filename and SHA-256, historical Close values and each future step's 10th/50th/90th percentiles. The newest 100 are listed in the interface; older snapshots remain on disk. `<profile>/predictions.json` stores machine-local settings and selections. Workspace export/import does not include models, prediction preferences or forecast snapshots; back up these folders separately when needed.

Malformed or unordered source timestamps, invalid Close values, insufficient closed history, duplicate CSV ranges for the same asset/period, model download errors and inference errors are reported. For legacy duplicate ranges, use Screener Refresh to consolidate the history before retrying. A changed source during inference prevents publishing a potentially inconsistent snapshot. Failed preparation never falls back to example data. Forecast values are estimates; an 80% model band is not a guarantee that future market prices remain inside it, and this feature does not establish trading profitability or send alerts.

## Save, export and recover

Workspace data lives at `$XDG_DATA_HOME/cryptodesk/workspace.sqlite`, normally `~/.local/share/cryptodesk/workspace.sqlite`, with user-only permissions. A local lock prevents another process from editing the same store. For an isolated profile use `./cryptodesk --data-dir /absolute/test-directory`.

Autosave uses 500 ms idle debounce with at most two seconds of deferral, ordered edit sequences and acknowledged SQLite revisions. Tab switches flush; native close captures viewports and awaits the final commit. When launched from a terminal, **Ctrl+C** follows that same save-and-close flow; **SIGTERM** also requests a graceful close. Interrupts received during startup are queued until the workspace can acknowledge its final save. A save failure keeps the app open with retry/discard options; repeated interrupts do not discard unsaved changes. A forced kill can lose pending frontend edits; the last acknowledged commit survives.

Import/export uses native JSON file dialogs. Imports are limited to 5 MiB, strictly validated, previewed, confirmed and transactionally replace the workspace with a consistent backup. Exports contain configuration only. At most five recovery snapshots are kept in the workspace database. Reset is explicit and confirmed. Invalid/future saved documents are preserved and open a recovery screen, with backup/import/reset choices. A physically unreadable database fails startup with an error and preserves the file.

For a portable backup, export JSON. To copy the database manually, close the app first and retain any `-wal`/`-shm` companion files; do not copy only a live main database file. Move a corrupt database and its companion files aside before an explicit fresh profile; never delete them as an automatic recovery shortcut.

## Boundaries and attribution

Memory caches, history request sizes, queues and rendered instances are bounded. The optional disk candle cache is persistent and can grow; it has no automatic deletion. Active series retain at most 10,000 bars in a moving window: older-history loads evict newer bars while preserving the selected historical range, and Return to live reloads the latest window. Full manual desktop, high-DPI and target-release coverage is recorded separately in STATUS.md; automated browser tests do not establish those checks. Exact window position on Wayland is best effort; normal size and maximized state are saved.

Charts by [TradingView](https://www.tradingview.com/), using Apache-2.0 Lightweight Charts. Its creator attribution remains visible. [Third-party notices](docs/THIRD_PARTY_NOTICES.md) and copied licenses ship with the archive. JForex credentials are used for authenticated market data. There is no trade execution, wallet, hosted TradingView client, paid feature gate, telemetry or automatic updater.
