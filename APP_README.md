# CryptoDesk

CryptoDesk is an Ubuntu and Windows desktop chart workspace for crypto spot/perpetual markets and Dukascopy forex, metals and CFDs built with Go, Wails v2, React/TypeScript, Lightweight Charts v5, and SQLite. Binance, Bybit, Coinbase and Hyperliquid use public feeds without API keys or accounts. The Dukascopy source uses your Dukascopy JForex Demo/Live credentials and the included Java bridge. Releases run without a development server.

Open the symbol dropdown to browse both **Spot** and **Perpetual** instruments on Binance and Bybit. Each row shows its market type on the right; identical names such as BTCUSDT remain separate choices. The chart keeps the selected market on save/restart and uses its own historical/live feed and candle cache. Binance USD-M/COIN-M and Bybit linear/inverse perpetuals are supported, including XAGUSDT silver contracts. Dated futures and options are excluded. Coinbase currently supplies spot instruments. Search by symbol, base/quote asset or market label. If a provider category is restricted, available symbols remain usable alongside an explicit warning and Retry discovery.

Select **Hyperliquid** in a chart's Exchange control to browse its complete public spot-pair catalog and active perpetual markets, including all discovered builder-deployed (HIP-3) DEXes. Discovery reads `spotMeta`, `perpDexs` and each DEX's `meta`; it does not use a fixed symbol list or require a wallet. Spot rows show token names and their native pair IDs, such as `HYPE/USDC · @107`. Perpetual names retain DEX prefixes such as `xyz:NVDA`, so markets with similar names stay independent. Native HyperCore token names (for example UBTC) are preserved. Delisted perpetuals are excluded. Discovery is paced to the provider's budget and can take tens of seconds; failures remain visible with Retry discovery. Hyperliquid H1, D1 and W1 charts also read retained Screener downloads when loading older history, independently of the optional chart cache. Daily downloads cannot supply intraday candles or another exchange's charts.

Hyperliquid supplies native trade OHLCV for **1m, 5m, 15m, 1h, 4h and 1d**. CryptoDesk derives **1w** from its daily candles to preserve Monday 00:00 UTC weeks; Hyperliquid’s native weeks start on Thursday. Weekly live prices update from daily snapshots while volume stays at the last REST-derived weekly total until reconciliation, explicitly marked provisional. Its public [candle history API](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint#candle-snapshot) retains only the **latest 5,000 native candles per interval** (about 3.5 days at 1m, or roughly 714 derived weeks from daily history). Scrolling cannot retrieve older provider history; closed candles already retained in the optional local cache remain available. Current candles are provisional and reconciled with REST. Live **Bid / Ask** are shown separately from trade candles using the unaggregated [public order book stream](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/websocket/subscriptions); empty sides display no price, and interrupted connections clear quotes. These are current quotes, not historical Bid/Ask candles. Only active charts subscribe; identical instruments share the upstream socket and order book subscription. Spot and perpetual chart settings, drawings and cache identities survive save/restart without a workspace migration.

Explicit live checks: `go run ./cmd/smoke -providers hyperliquid -market spot -instrument @107 -duration 20s` or `-market perpetual -instrument BTC`; a builder market can be selected by its exact discovered DEX-qualified ID. These commands use real public data and report candle and bid/ask observations separately.

**First launch has exactly one tab and one chart in a 1×1 grid.** Add tabs and charts as needed, up to 20 tabs and 9 charts per tab. Selecting a larger grid adds empty controls, not chart configurations. New tabs start with one chart. Later launches restore your actual saved workspace.

The original specification bundle is retained at the repository root. [STATUS.md](STATUS.md) describes observed verification and remaining limits.

## Run the built release

Run the root `./cryptodesk` produced by `./build.sh`, or extract `cryptodesk-X.Y.Z-linux-amd64.tar.gz` and run `./cryptodesk` inside its directory. This small archive requires compatible GTK3, WebKitGTK 4.1, libsoup3 and Linux desktop runtime libraries. Tested local build environment: Ubuntu 26.04.1 x86_64, Wayland, GTK 3.24.52, WebKitGTK 2.52.6.

On Ubuntu Desktop **24.04 or 26.04 x64**, install the system runtime dependencies once:

```bash
sudo apt update
sudo apt install -y \
  libgtk-3-0t64 libwebkit2gtk-4.1-0 libsoup-3.0-0 \
  glib-networking gsettings-desktop-schemas dconf-gsettings-backend \
  ca-certificates fonts-dejavu-core \
  libnss3 libnspr4 libasound2t64 libxss1
```

GTK3 provides the desktop window, WebKitGTK the embedded interface/JavaScript engine, and libsoup3 plus GLib networking the webview's HTTP/TLS support. NSS/NSPR, ALSA and X11 support libraries serve the private Screener Chromium. APT installs transitive dependencies automatically; the [Ubuntu package catalog](https://packages.ubuntu.com/noble/amd64/libwebkit2gtk-4.1-0) lists the WebKitGTK runtime dependencies. Keep the supplied `screener-runtime` folder beside the application: Node, dukascopy-node, trading-signals and Chromium are already included.

For **Dukascopy charts**, also install **Java 17 or newer**:

```bash
sudo apt install -y openjdk-17-jre-headless
java -version
```

A JRE is sufficient to run Dukascopy charts; building the bridge needs a JDK. Linux prefers `/usr/bin/java`, then `java` on `PATH`, then `JAVA_HOME/bin/java`. This keeps an IDE's JDK from replacing the system runtime. On Windows, install [Eclipse Temurin 17 x64](https://adoptium.net/temurin/releases/?version=17&os=windows&arch=x64) or another compatible Java runtime; Java on `PATH` takes priority over `JAVA_HOME`. Restart the app after changing Java. The JForex desktop platform is not required. Crypto charts, Screener and Predictions do not require Java.

Use a graphical desktop session with working graphics drivers. GitHub releases build on Ubuntu 24.04; locally built archives require a glibc version compatible with their build host. Workspace storage remains in the normal user profile unless `--data-dir` is supplied. The separate Linux archive with bundled GTK/WebKit has been retired.

Launch first shows a lightweight branded loading screen, followed by the current step, such as **Opening workspace database…**, **Reading saved layout…** or **Starting chart services…**. The actual saved workspace opens as soon as its storage and chart services are ready. Screener recovery, saved forecasts, Live Alerts and candle-cache validation continue in the background; a progress notice identifies unfinished services and preserves restoration errors. A tool waits for its own saved state before accepting operations. Hyperliquid charts wait for retained Screener history before using it, while other providers can connect independently. Application-file failures offer **Retry loading**; workspace recovery retains its existing backup/import/reset choices. Native GUI runtime setup remains a prerequisite to creating the window.

When closing, **Closing gracefully...** appears while final settings save and background cleanup finish. The app now cancels market streams, JForex, Live Alerts, predictions and Screener workers concurrently, then drains candle writes and releases workspace storage. Save failures retain the existing Retry / Discard / Keep open choices; the closing message clears when closing is cancelled. Slow storage or provider/process cleanup can still delay exit.

Optional user-local installation for the **Linux archive** (updates the desktop launcher and its complete app/bridge bundle):

```bash
./install-user.sh --dry-run
./install-user.sh
```

Linux and Windows first read the **`jforex-runtime` folder beside the actual executable**. This keeps a local `./build.sh` output and an extracted release paired with the bridge built for that app. Launcher symlinks resolve to the real executable; the current working directory and `--data-dir` never select another bridge. A standalone Linux executable without a sibling runtime can still use `$HOME/.local/share/cryptodesk-app/jforex-runtime`, or the equivalent under an absolute `XDG_DATA_HOME`. An existing damaged sibling folder is reported rather than silently replaced by a different installation. Explicit `CRYPTODESK_JFOREX_RUNTIME` overrides retain priority and pinned-manifest validation.

**Local builds can run directly.** `./build.sh` places the matching bridge beside the root executable; `scripts/build-linux.sh` also pairs `build/bin/cryptodesk` with its bridge. `scripts/dev.sh` builds/selects a private development bridge unless you supplied an explicit override. Run the root `./cryptodesk`, or the complete extracted release, without a separate bridge installation step. Use `./scripts/install-user.sh` only to update the installed app/desktop launcher. Fully restart an already running app to load its new code.

The former occasional local-build “update JForex” error came from selecting an older user-installed bridge after rebuilding the app. The vendor SDK version could be identical while CryptoDesk’s bridge capabilities differed. Selecting the executable’s matching bundle removes that mismatch; the vendor SDK remains pinned at **3.6.51 / API 2.13.99**, with the existing verified dependency cache retained. The compatibility handshake still runs before credentials or PIN requests.

This writes the app under `$XDG_DATA_HOME/cryptodesk-app` (normally `~/.local/share/cryptodesk-app`), registers its application launcher and installs the same diamond logo shown in the app's top-left corner. The launcher uses an absolute PNG icon path, with SVG and eight PNG sizes also registered in the user icon theme. The native window embeds a smaller copy that GTK accepts on X11; the matching `cryptodesk` desktop identity provides Wayland taskbar association. Windows builds carry the same logo in their executable resources.

If your configured desktop folder exists, installation also creates an executable `cryptodesk.desktop` shortcut there, preserving any differing existing shortcut. It sets that file's trusted metadata when supported; your desktop may still require **Allow Launching**. Per-user icon/application metadata is refreshed when the desktop tools are available. No system settings or workspace data are changed. The installer copies the complete private Screener runtime and the five-file JForex bridge, validating its inventory before installation and restoring the previous bridge if installation fails. The original extraction folder can then be removed.

Run the installer again after rebuilding or downloading an updated archive, then close and reopen CryptoDesk. If an existing pinned taskbar entry retains an old icon, unpin it and pin the newly installed **CryptoDesk** application entry. Installation does not start the app. Source-checkout equivalent: `scripts/install-user.sh --dry-run` after building.

## Downloads and release versions

The main [README](https://github.com/neodix42/charting#download) links to the [latest release](https://github.com/neodix42/charting/releases/latest). Pushing commits to `main` runs the [release workflow](.github/workflows/release.yml): build the standard Linux archive and Windows ZIP, assign `v0.1.0` initially and increment subsequent patch tags, verify package contents, architecture, version and provenance, then publish both versioned packages together. Test suites run separately and do not gate publication. `SHA256SUMS` verifies the archives and `release.json` records their version, source commit and hashes. Historical completed releases, including older bundled Linux downloads, remain preserved and checksum-verified. The workflow assumes `main` is the default branch. Superseded queued commits or older workflow contents are skipped in favor of the newer push; a workflow change during a build stops publication before remote writes.

The header displays the installed build's `vX.Y.Z` release tag beside the CryptoDesk name. It is embedded at build time and works offline; it does not change when a newer release is published. Packaging verifies that the UI version matches the selected release, and diagnostics reports the same compiled version.

Local builds use the baseline in `VERSION` (currently `0.1.0`). Set `CRYPTODESK_VERSION=X.Y.Z` to override it for either build script; the header, output filename, package manifest and Windows product version follow this value. Release CI passes its selected version without making source-version bump commits. Hosted execution and Windows GUI checks are recorded separately in [STATUS.md](STATUS.md).

The independent [Tests workflow](.github/workflows/tests.yml) runs on `main` pushes, pull requests and manual dispatch. It runs all automated suites, including browser interactions and offline verification of the packaged Screener enrichment/Refresh runtime. Its artifacts are **diagnostics-runtime-linux-amd64** for runtime reports and **diagnostics-browser-linux-amd64** for browser reports and failure screenshots/traces; diagnostics are retained on success or failure. A test failure does not stop the release workflow. Disposable Linux CI runners check the required suites and choose a reachable HTTPS archive from a fixed list (Ubuntu, kernel.org and Princeton mirrors), with Ubuntu signing keys and repository suites retained; failed package-list updates stop setup instead of continuing from stale lists. Network requests and dependency setup are bounded. The runner configuration helper refuses normal local invocation and is not used by local builds. The retired GTK/WebKit bundle's namespace provisioning, runtime redistribution and source collection no longer run.

## Build and develop

Pinned versions: Go module/CLI Wails 2.17.0; React 19.3.1; Lightweight Charts 5.2.1; SQLite Go driver modernc.org/sqlite 1.60.1. This checkout was built with Go 1.26.8, Node 24.19.0 and npm 11.17.0. Frontend and Go lockfiles are included.

Install Go, Python 3.12+, **JDK 17+** with `java` and `javac`, a C compiler and pkg-config. On Ubuntu, `sudo apt install openjdk-17-jdk-headless` supplies the Java build tools. Build/dev/test scripts check that both Node and npm run. If either is missing or incompatible, they download the official Node 24.19.0 bundle (including npm), verify its pinned SHA-256, and reuse it under `.tools/` on later runs. The selected `bin` directory is exported to Wails and its child processes. No shell-profile edits, global npm installation or IDE runtime paths are needed. Initial download requires access to `nodejs.org`; alternatively provide Node 24 LTS with npm on your terminal's PATH.

Linux native builds also require GTK3 and WebKitGTK 4.1 development packages; the standard Ubuntu package names are `libgtk-3-dev` and `libwebkit2gtk-4.1-dev`. Installing OS packages is a separate user/admin action.

On an Ubuntu machine which already has the corresponding runtime libraries, `scripts/bootstrap-native-sdk.sh` is an optional unprivileged alternative: it downloads exact currently resolved Ubuntu development-package archives and extracts them under ignored `.tools/native`; it does not install packages or change the OS. `scripts/native-env.sh` scopes those headers/linker paths to the invoking process. This SDK path was used in the test environment. Repositories/network access are needed for bootstrap; package versions are recorded in `.tools/native/package-versions.txt`.

```bash
./build.sh                   # ready-to-run app + standard Linux archive + checksums in repo root
./win-build.sh               # cross-build Windows x64 ZIP with English WebView2 locale packs
scripts/build-linux.sh       # pinned local CLI, production frontend + desktop + archive
scripts/dev.sh               # desktop development
scripts/test.sh              # deterministic Go race/vet + frontend checks/build
cd frontend && npm run test:e2e
```

`./build.sh` works from any current directory and publishes `cryptodesk`, its sibling `jforex-runtime` folder, `cryptodesk-X.Y.Z-linux-amd64.tar.gz`, and `cryptodesk-SHA256SUMS` at the repository root. Launch `./cryptodesk`, or copy the complete archive to a compatible Linux desktop, extract it and launch the included executable. Verify root outputs with `sha256sum -c cryptodesk-SHA256SUMS`.

Both Linux and Windows builds compile our JForex bridge with Java 17 bytecode, using checksum-pinned SDK **3.6.51 / API 2.13.99** artifacts from Dukascopy's official Maven repository and Maven Central. The approximately **43 MB** SDK build cache lives under `.tools/jforex-sdk/cache`; vendor SDK JARs are excluded from release archives. Each package contains only `cryptodesk-jforex.jar`, `SDK-ARTIFACTS.json`, `JFOREX-PROVENANCE.json`, `LICENSE` and `THIRD_PARTY_NOTICES.md` inside `jforex-runtime`. Package validation checks all five files, their hashes and matching `version.json` provenance.

Release builds and Tests share a persistent **verified JForex SDK cache** keyed by the checked-in artifact manifest. They reuse the last downloaded client and dependencies without contacting the vendor when all pinned files are present. A newer vendor release is not required or selected automatically: the reviewed **3.6.51 / 2.13.99** versions remain in use until an explicit upgrade. Missing pinned files are downloaded atomically; a failed download never removes a working cached file. Only manifest-listed JARs enter the build/test classpath, so retaining older downloaded files cannot mix SDK versions. The complete verified cache is saved before subsequent build/test steps, including when those later steps fail. GitHub may evict inactive Actions caches; the retained local cache is independent.

If the vendor repository is unavailable and CI has no cached copy, maintainers can seed it from an existing complete local cache. The **Seed verified JForex cache** workflow imports only the exact 51 manifest-pinned files after checking both the transfer checksum and every artifact checksum. Use a temporary **draft** release for this private transfer, then delete that draft after the workflow succeeds. Vendor SDK JARs stay out of product releases and source control:

```bash
SDK_CACHE_SHA256="$(python3 scripts/jforex_cache.py --export .tools/jforex-sdk-cache.tar.gz)"
gh release create jforex-sdk-cache-seed .tools/jforex-sdk-cache.tar.gz --draft --target main --title 'Temporary verified SDK cache' --notes 'Private transfer into the CI dependency cache; delete after import.'
gh workflow run jforex-cache.yml -f seed_release=jforex-sdk-cache-seed -f archive_sha256="$SDK_CACHE_SHA256"
# After the seed workflow succeeds:
gh release delete jforex-sdk-cache-seed --yes
```

The export refuses to overwrite an existing transfer file; keep or move aside the previous transfer before repeating these commands. Keep the working `.tools/jforex-sdk/cache` directory. Ordinary builds and Tests retain read-only repository permissions; only this manually dispatched maintenance job needs write permission to read unpublished draft assets. Existing user-profile SDK files and credentials are not involved.


Chart history timeouts retry automatically while the chart is subscribed, using delays of 2, 4, 8, 16, then at most 30 seconds between failed attempts. Live Bid quotes continue and the status shows reconciliation/retry until history finishes. Successful closed-history chunks stay loaded; retries resume from their proven checkpoint. An empty initial response retries the initial history load. Closing the chart/tab or disconnecting cancels retries. Use the complete rebuilt app/bridge bundle and restart the app to use this behavior.

For source-checkout development, build with `./build.sh` and launch the root `./cryptodesk`, or use `scripts/dev.sh`. Installing the built release is optional and updates the desktop launcher. `python3 scripts/jforex_bundle.py --test` verifies the bridge and actual SDK bootstrap without account credentials; initial SDK downloads still need network access. To deliberately test another build in isolation, run `python3 scripts/jforex_bundle.py --output jforex-runtime` and set `CRYPTODESK_JFOREX_RUNTIME` to that complete folder's absolute path. This explicit override is independent of the Screener runtime override; normal discovery never selects a checkout's JAR.

Binding generation runs without opening a workspace database, so building while CryptoDesk is open does not conflict with its workspace lock.

`./build.sh` checks for a newer stable `dukascopy-node` release before compilation and adopts it only after staged compatibility checks and offline runtime tests pass. Set `CRYPTODESK_UPDATE_SCREENER=0` to keep the current exact pin; release CI does this for consistent Linux/Windows packages. See [Updating the Screener downloader](README.md#updating-the-screener-downloader) for update behavior, bundled-version checks and installation instructions.

For Windows, run `./win-build.sh` on Ubuntu with Go, Python 3.12+, **JDK 17+** and `7z` (Ubuntu package `7zip`). It produces `cryptodesk-X.Y.Z-windows-amd64.zip` and `cryptodesk-Windows-SHA256SUMS` in the root. The ZIP includes Microsoft Fixed Version WebView2 with English (`en-US` and `en-GB`) locale packs; other locale PAKs are omitted. The complete source runtime is verified against its pinned version, SHA-256 and inventory before reducing only the staged package. Shared resources and all licenses are retained. Build sources are copied to a temporary directory, preserving existing generated bindings, uncommitted files and Linux outputs. The script uses project-local Node/npm/Wails and does not install system packages. Fresh machines download the pinned Windows-only Go WebView2 module before preparing the English-language overlay; a prefilled Go module cache is not required, and normal Go checksum/source verification remains enabled. Initial runtime download is about 300 MB; the complete verified runtime remains cached under `.tools/webview2`. Use `./win-build.sh --webview2-cab /path/to/pinned.cab` for a local copy of the exact pinned runtime.

On Windows, extract the **whole ZIP** to a local writable folder and launch `cryptodesk.exe`. Keep `WebView2`, `screener-runtime`, `jforex-runtime` and `portable.marker` beside it; the workspace and browser profile live in its `data` directory. This needs no separate WebView2 installation; Dukascopy charts additionally need the separately installed Java runtime. Windows 10 startup applies Microsoft's required read/execute grants to the bundled runtime directory; Windows 11 needs no grants. Fixed runtime updates require a new reviewed runtime pin and rebuild. The executable is unsigned, and cross-compilation on Ubuntu does not replace Windows runtime testing. Full details: [Windows portable build and usage](docs/WINDOWS_PORTABLE.md).

The underlying `scripts/build-linux.sh` also retains `build/bin/cryptodesk` and the distribution under `release/`, including checksums, licenses and a version manifest. Build scripts never use sudo or a system package installation. The CLI is installed into project-local `.tools/` if absent. Normal builds contain local assets and no fixture bridge.

## Use

Use the **＋** immediately after the tabs, or Ctrl+T, to create a single-chart tab; Add Chart or Ctrl+Shift+N adds one chart. The tabs and **＋** share one horizontally scrolling strip, so scroll along the row to reach later tabs. Ctrl+Tab / Ctrl+Shift+Tab changes tab; Ctrl+W closes the active tab with confirmation. **Double-click a tab to rename it. Middle-click any tab** to close that tab and all its charts without a confirmation dialog; an inactive target stays inactive. The final tab cannot be closed. Each chart has a larger **×** button that removes the chart immediately without confirmation; the final chart in a tab stays protected. Shortcuts stay inactive in editors/selectors. Duplicate a tab from the header or drag tabs to reorder; drag chart headers to reorder charts. Row/column splitters resize tracks. Maximize chart temporarily and restore it without changing the saved grid.

Each chart has its own exchange, searchable native instrument, horizontal period buttons (`1m`, `5m`, `15m`, `1h`, `4h`, `1d`, `1w`), volume, candlestick/line style and linear/log scale. The buttons stay in the chart header row; small chart headers scroll horizontally. Drag/pan/zoom the chart; scrolling left loads older history. Return to live follows current bars. Manual price scaling and time viewports are saved. Settings provides theme, IANA/system timezone, optional local candle storage, JSON import/export/reset and diagnostics. Candle boundaries remain UTC regardless of display timezone.

**Settings → Chart right gap** sets the space between the latest candle and the chart’s right edge for every tab. Choose **Bars** (default **10**) or **Pixels**, enter a whole number, and press **Apply**. All current charts update immediately, including maximized siblings; inactive tabs use the same setting when opened. Changing the gap returns all charts to live while retaining their zoom and price settings. The preference survives restart and JSON export/import. Accepted values are 0–500 bars or 0–5,000 CSS pixels; a gap that exceeds the available chart width is reduced to keep the latest candle visible. Ichimoku’s projected cloud does not move the gap’s anchor away from the latest price candle.

Centered in the top header alongside the CryptoDesk logo, shared period buttons and an **Indicators** dropdown apply to every existing chart in the current tab, including charts hidden by maximization. Grid, Add chart and Duplicate controls sit to their right, immediately before the save indicator. Its width stays fixed while changes are pending, saving, saved or awaiting retry, keeping neighboring controls in place. Narrow windows use compact action icons with tooltips. Tab names remain in the tab row. A period click updates all those charts immediately and returns them to live view. The shared period is highlighted only when every chart agrees; individual chart controls can still override it. For an indicator, configure its parameters once and press **OK** to add an independent instance to every chart in the tab. Existing indicators are retained, other tabs stay unchanged, and all changes are saved. If any chart already has 12 indicators, the shared dropdown is disabled until an indicator is removed from that chart.

Weekly candles start Monday at 00:00 UTC. Binance, Bybit and Dukascopy provide native weekly candles. Coinbase weekly history is derived from actual daily candles, with live updates from its public trades; incomplete weekly coverage remains provisional.

### Drawing tools

Every chart has a **Draw** toolbar: **Arrow up**, **Arrow down**, **Horizontal line** and **Trendline**. Choose a tool, then click the price chart to place it. A trendline uses two clicks, one for each end, with a preview between them. Press **Esc** or choose **Cursor** to cancel an unfinished drawing and resume panning. **Undo drawing** removes the last drawing on the current instrument; **Clear drawings** removes all drawings on that instrument.

**Single-click a drawing to select it.** Select an arrow by its tip or shaft, a horizontal line anywhere along it, or a trendline along its segment. Click **Delete** in that chart's toolbar or press **Delete / Del** to remove the selected item. Keyboard deletion is suspended while typing or using a dialog. Clicking empty chart space or pressing **Esc** clears the selection.

Selected lines show square handles. **Drag either endpoint and release** to change its position or length. A full-width horizontal line becomes a finite horizontal segment when an endpoint is dragged; it stays horizontal as you adjust either end. **Esc** or **Cursor** cancels an unfinished adjustment. Changes are saved after release.

To reposition a whole item, **double-click the drawing**, move the pointer, then **click to place it**. Trendlines and finite horizontal segments keep their shape and the point where you grabbed them. **Esc**, **Cursor** or a chart header control cancels the move and keeps the previous position. Clicking **Save** during a move or endpoint adjustment saves the previous completed position and keeps the preview active. Completed edits retain the drawing's identity, and both edits and deletions restore after restart.

Completed drawings autosave to SQLite and restore after restart, tab switches and JSON export/import. Positions use UTC times and prices, so zooming, resizing and changing timeframes preserve their anchors. Drawings belong to their chart, exchange, market and instrument: switching symbols hides unrelated drawings and switching back restores them. Add Chart starts without drawings; Duplicate Tab copies them independently. Each chart supports up to 100 saved drawings across its instruments.

### Indicators

Each chart has an **Indicators** dropdown. Select SMA, EMA, Low, High, Ichimoku Cloud or MACD, adjust its parameters, then press **OK** to add it. SMA and EMA also offer **Line width** from **1–4 px**, default **2 px**, in both individual and shared dialogs. Cancel leaves the chart unchanged. Click an applied indicator's label to edit it, or its × to remove it. Multiple instances can use different periods, colors and line widths; settings are independent per chart and survive restart and JSON export/import. There are at most 12 indicators per chart to bound rendering work. Existing SMA/EMA instances without a width retain their two-pixel appearance.

| Indicator | Default parameters | Display |
|---|---|---|
| SMA | Close-price period 200, red, line width 2 px | Price overlay |
| EMA | Close-price period 20, line width 2 px | Price overlay |
| Low | Period 10 | Lowest candle low of the last N bars, including the current bar |
| High | Period 10 | Highest candle high of the last N bars, including the current bar |
| Ichimoku Cloud | Conversion 9, base 26, leading span B 52, displacement 26 | Conversion/base/leading/lagging lines and green/red cloud between the leading spans |
| MACD | Fast 12, slow 26, signal 9 | Separate pane with MACD/signal lines, histogram and zero baseline |

Intraday charts also offer **Today's low**, **Today's high**, **Previous day low**, **Previous day high**, **Week's low**, **Week's high**, **Previous week low**, **Previous week high**, **2 days ago low/high** and **3 days ago low/high**. These parameterless price overlays have a color setting. Days reset at **00:00 UTC** and weeks at **Monday 00:00 UTC**, independently of the display timezone. Today's/this week's extrema use only that period's candles up to the current bar, including a provisional live candle; they never use later bars. Previous ranges stay fixed during the current period and refer to the preceding available completed day/week, skipping periods with no bars during market closures. A partial leading period stays blank and cannot become a previous-period value. Loading enough earlier history fills the range.

These choices are disabled on D1/W1 charts. Changing an existing chart to D1/W1 preserves its range settings with an **intraday only** label and hides their plots; returning to an intraday timeframe restores them. The shared tab indicator menu enables these choices when every chart in that tab uses an intraday timeframe. Ordinary history windows remain capped at 10,000 bars; calendar overlays can request up to **20,161** one-minute bars to include a complete previous week. History loads use bounded pages and the existing feed lease. A new listing or provider history limit can leave ranges unavailable; no missing bars or prices are fabricated.

**Visible components** in the Ichimoku and MACD parameter dialogs controls each plotted component independently. Ichimoku offers conversion, base, leading span A, leading span B, lagging line and cloud fill: to show only the base or conversion line, leave only that checkbox selected. MACD offers the MACD line, signal line, histogram and zero line. Its Fast/Slow periods remain calculation inputs; their values still apply when a plot is hidden.

Visibility choices apply when you press **OK**; Cancel or Escape discards them. They persist per indicator through restart, duplication and JSON export/import, and the shared Indicators dialog applies the chosen visibility to every chart in the current tab. Existing indicators start with every component visible. Hiding every component keeps its configuration available for later editing. Hidden plots do not affect autoscaling or leave projected Ichimoku timestamps on the chart. Calculations, chart subscriptions and MACD pane sizes are retained.

Drag the separator above a MACD pane to resize it. Each MACD instance saves its own height relative to the main price pane, restoring the same proportions after tab switches, parameter edits, restart and JSON export/import. The proportions adapt when the chart or window is resized.

New SMA instances default to red and 200 bars; saved periods and colors remain unchanged. Low/High wait for a full period, then update their rolling wick extrema on each candle correction.

Periods count chart candles, from 1 to 2,000; Ichimoku displacement is 0–500 bars. MACD fast must be smaller than slow. Color controls the indicator's primary line. Long periods request older candles automatically, with a visible warm-up/history status when available data is insufficient. Calculations use the loaded candle window, including the current provisional candle, and update after candle corrections. EMA seeds from a full SMA window before applying `2 / (period + 1)`; MACD's signal uses the same EMA convention. Ichimoku displaces leading spans forward and the close backward by the configured number of bars, extrapolating future timestamps only for the projected cloud. The cloud contains derived values, never invented future prices. Earlier history can change an EMA's seed, so results can differ slightly from chart services with a different seed/history window.

Existing workspaces without an `indicators` field continue to load unchanged. Indicator calculations are local; no additional account, data feed or subscription is required. Indicator changes reuse the existing chart and feed.

Only the active tab mounts charts and requests leases. Identical feeds share data and provider sockets; hidden tab leases release after a cancellable two-second grace. Cached data and chart settings remain. A larger grid never creates hidden subscriptions.

Live status and public-data details stay in the chart’s bottom-left footer, including when the cursor is over blank space or a future cloud span. Connection progress and feed failures retain their visible messages and retry controls.

Provider failures remain visible in their chart. Retry or reselect without losing configuration. Prices are never synthesized as a fallback. Coinbase live intervals derive from deduplicated trades, rather than relabelling its five-minute candle channel. An initial/reconnected partial bucket has provisional volume: the last REST snapshot or explicitly observed-only trades, never REST plus all buffered trade volume. Public Coinbase aliased USDC products are labelled/rejected; choose the actual USD product explicitly.

### Prices, history and storage

Historical loads use the official [JForex candle history API](https://www.dukascopy.com/client/javadoc3/com/dukascopy/api/IHistory.html) independently of connection controls and live quotes, with a 45-second deadline and cancellation. Missing completed D1/W1 bars are fetched as native Bid candles and published first. The unfinished W1 candle combines completed daily bars with the current day; the unfinished day combines completed hourly bars and at most 60 minute candles from its current hour. This avoids asking the SDK to reconstruct an entire unfinished day or week. Only the currently forming minute may require finer SDK data. The composed D1/W1 candle remains provisional until the native closed candle arrives. H1/H4 charts continue requesting their selected native period; opening D1/W1 does not preload separate intraday charts. Small missing-range requests fetch just that range instead of a full history page. The footer stays **reconciling** while the current snapshot loads and reports any failure even when live quotes keep arriving. Live candles update from genuine Bid ticks without waiting for the SDK's historical cache. Until SDK candle data reconciles them, these updates are **provisional**: opening context and the last known SDK volume are retained where available; unavailable volume is zero. Native closed-bar updates supply the authoritative OHLCV. A late history seed preserves newer quotes and closed-bar corrections. Quote freshness comes from observed ticks rather than a blocking last-tick history lookup.

All seven chart periods are supported: **1m, 5m, 15m, 1h, 4h, 1d and 1w**. Historical candles and live updates consistently use **Bid** prices. Native weekly candles start Monday at 00:00 UTC. Market closures remain gaps; no weekend or holiday bars are invented. **Quote** freshness, connection errors, reconnection and market-closed status appear in the chart footer. Volume retains the SDK's native values: forex quote volume is displayed in millions; other instruments show provider units. It is not treated as centralized exchange trade volume.

The JForex bridge runs only for requested Dukascopy discovery/history/quotes. Inactive chart tabs release their subscriptions. These authenticated charts automatically save their accepted closed Bid candles to a private SQLite chart cache, scoped by environment and a hash of the username. Reopening a chart or restarting CryptoDesk displays this saved history immediately while the account reconnects. After the initial history load, the bridge requests only the missing suffix with a small overlap, in bounded chunks; it does not reload the full 500-bar seed on every open. Completed catch-up checkpoints survive restart, including empty weekend ranges. A failed or canceled catch-up preserves saved candles and resumes from its last confirmed checkpoint; a newer live candle alone cannot hide an unfinished gap. Older downloaded chart pages also retain successful-query coverage for local reuse. Current/open candles stay provisional in memory and are refreshed from the provider. These caches are separate from the optional public-crypto SQLite candle cache and remain active when Settings → Storage is disabled. Cache errors remain visible, and existing damaged files are preserved rather than replaced. Cached prices are not reported as fresh live quotes. They also do not modify Screener CSVs or change dukascopy-node's WAF/rate-limit handling.

Hyperliquid perpetual tickets provide a **Leverage** dropdown from **1×** through the selected asset’s current metadata maximum, shown beside the control as **Max N×**. Limits load from the selected network and exact native/DEX market; unknown or stale limits disable review until refreshed. A lower refreshed limit adjusts an out-of-range draft selection; the backend rechecks the current maximum before any signed action.

Hyperliquid tickets also show a **Hyperliquid balances** overview for **Main perps**, **xyz**, **para** and **Spot**, with other discovered DEXes under **Other DEXs**. Each balance retains its own collateral/token and availability; different currencies are never added together. A failed or stale read displays an explanation instead of zero. The overview refreshes every 30 seconds while editing and through **Refresh balances**; order and transfer reviews keep their reviewed snapshots. Your **Manual / Standard** account mode has separate balances for each DEX. Shared account modes show shared token holdings without presenting duplicate DEX balances as independent funds.

Use **Move assets** in that overview to transfer within your configured Hyperliquid account. There are no separate DEX deposit addresses to discover: **From** and **To** identify internal balances belonging to the same public account address displayed in the ticket. For example, choose **Main perps → xyz**, select their matching collateral token, enter **Amount** (or **Max**), then **Review transfer** and **Confirm transfer**. To fund Spot, select **Spot** as the destination; reverse the route to move supported collateral back. The review shows the network, account, token identity, source, destination, amount and remaining source balance. Only compatible routes appear: a perpetual DEX accepts its own collateral token, so moving USDC cannot turn it into USDH or another currency. Buy the required token separately if the two DEXes use different collateral.

Transfers require Manual / Standard account mode and the existing approved API wallet. Hyperliquid's documented [agent-send-asset action](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint#agent-send-asset) restricts the destination to that same account. The app supplies that address internally; there is no external destination-address field. It rechecks approval, token precision and the available source balance at confirmation. Reviews expire after one minute, are consumed once and are durably recorded before sending. Moving collateral can affect existing positions, so review the remaining balance. An uncertain response never triggers an automatic retry: refresh balances and inspect the exchange before starting another transfer. Starting a transfer discards an old order review while preserving the editable order inputs; review the order again after funding changes.

Hyperliquid SL/TP rows show signed entry **bps** and gross position P/L in the market’s verified **settlement collateral**, such as **USDC**, **USDT**, **USDH** or another token named by exchange metadata. The account can hold multiple assets; the selected perpetual DEX determines the settlement currency. Core perpetual prices may use a USDT oracle while P/L settles numerically in USDC; the contract applies no USDT/USDC exchange-rate conversion. Spot denomination comes from the pair’s actual quote token and its leverage remains fixed at 1×; attached spot SL/TP is still unsupported. Missing token metadata displays settlement amounts as unavailable rather than inventing a USDC/USDT denomination.

Draft quantity and SL/TP edits recalculate immediately; market quotes and metadata refresh every ten seconds and via **Refresh quote**. Estimates appear beside the levels in both the form and reviewed order. Reviews keep their quoted entry/currency snapshot until explicit Edit/Refresh discards the old confirmation. Estimated P/L uses base-unit size without multiplying leverage again, and excludes fees, funding and slippage.

The order ticket also shows **Available balance**, **Margin required** and **Liquidation price**, with a timestamp and each value's source or limitation. Account reads refresh every ten seconds; quantity/leverage changes update supported projections. Reviews contain their own account snapshot. Empty fields mean unavailable, while a confirmed zero is displayed as zero. These reads do not place orders or change leverage.

For classic Hyperliquid perpetual accounts, available balance is the selected DEX's withdrawable collateral. A proposed new isolated position on a verified flat instrument shows estimated initial margin (`quantity × entry / leverage`) and a liquidation price using the exchange's maintenance-margin tiers. Fees, funding and slippage are excluded. Existing positions can net with the proposed trade, so these projections are unavailable in that case. Shared-collateral account modes show verified token holdings separately without treating them as free trading margin. Spot shows unheld quote tokens for Buy or base tokens for Sell; spot liquidation is not applicable.

Hyperliquid perpetual trades use isolated leverage and an immediate-or-cancel entry capped at 1% slippage, with optional reduce-only market-trigger SL/TP. The confirmation explains that existing exchange positions are netted. Spot uses balances: Sell sells owned units, without borrowing/shorting, leverage or perpetual-style SL/TP brackets. **Testnet spot trading is unavailable from these mainnet chart IDs** because the same `@index` may identify a different token on testnet. Perpetual instruments resolve by their exact native ticker/DEX on the selected network; review the network before confirming. Hyperliquid chart feeds themselves remain mainnet public data; the trade preview uses the selected trading network.

Dukascopy reuses **Settings → Dukascopy** JForex Demo/Live credentials. Market orders use the instrument’s SDK size rules and attach the requested SL/TP to the main order; order quantity is base units, not lots. **Account leverage is read-only**: JForex does not expose per-order leverage selection. Set position size with Quantity and review the actual account leverage. Use the matching JForex bridge beside the rebuilt executable or in the complete extracted release, then restart; update the desktop launcher with the installer only if needed. An older installed bridge remains usable for market data but refuses trading with an explicit update message. Connection/PIN requirements still apply.

Dukascopy order tickets show estimated P/L beside **Stop loss** and **Take profit**, both while editing and in the final review: signed **basis points (bps)** of entry and the amount in the actual SDK account currency (for example EUR or USD). One basis point is 0.01% of entry. Buy/sell direction is respected: `bps = direction × (level − entry) / entry × 10,000`; `account P/L = direction × (level − entry) × quantity in base units × current SDK quote-to-account conversion`. Leverage is not multiplied into P/L again. These are gross estimates using current conversion rates, before commissions, financing and execution slippage.

Quantity, SL and TP edits recalculate immediately. While editing, the market entry and conversion refresh every ten seconds; **Refresh quote** requests a new quote explicitly. A reviewed order keeps its own quote/conversion snapshot until you choose **Edit order** or **Refresh quote**, both of which discard the old confirmation and require review again. Missing/stale conversion data displays **Account amount unavailable** rather than guessing a currency or a 1:1 rate; delayed editing quotes lose their monetary estimate after 30 seconds. This feature needs the updated JForex bridge: install the matching build and restart as described above. Quote/valuation calls are read-only and do not place orders.

Dukascopy **Available balance** is free margin, calculated from SDK equity minus used margin in the account currency. The ticket separately shows the SDK account balance (previous end-of-day processing), current equity and used margin; these fields update asynchronously and do not promise withdrawable cash. Balance retrieval is independent of SL/TP conversion. The account-metrics panel reserves its space while loading and updating, so delayed values or errors do not move the Review order button. Long diagnostics can be scrolled inside the panel with a pointer or keyboard. Same quote/account currencies need no FX conversion; otherwise the ticket verifies SDK rates against fresh FX quotes and can use the verified quote route when the pip helper does not support a CFD. Conversion failures now identify the missing currency/FX quote. The pinned JForex SDK supplies neither a reliable pre-trade required-margin quote nor a standalone order liquidation price, so the ticket explains those limitations instead of calculating them from account leverage. Use the complete matching app/bridge bundle and restart to use account metrics.

Matching **Dukascopy** and **Hyperliquid perpetual** charts automatically show horizontal **Long/Short entry**, **SL** and **TP** lines for open trades recorded in this profile, with order IDs and instrument-formatted prices. The lines use the actual filled entry and the trade’s recorded protective levels. Existing open records are restored after restart; a newly confirmed chart order refreshes its levels immediately. Dukascopy refreshes its SDK protective prices; Hyperliquid uses the protection recorded for that platform entry, so subsequent external edits to its protective orders are not discovered by this overlay. Spot executions do not represent separately open positions and have no position-level overlay.

Levels are scoped to the matching asset/market, configured account and environment. Only the active chart grid shares a status check, every 20 seconds; identical assets across timeframes do not duplicate exchange requests. Closed positions disappear after reconciliation, and partial exits retain the remaining position’s entry and protection. Switching source/account clears old levels, pending reads cannot restore them, and stale/unverifiable statuses hide the lines with an explanation. Unavailable SL or TP values are omitted. Saved drawings, indicators, chart viewports and market subscriptions remain independent of the overlay.

Trading and internal Hyperliquid transfers are user-initiated only; Live Alerts, drawings, indicators and predictions never place orders or move funds. No automated trading or external withdrawals are implemented. Automated checks use synthetic credentials and mocked transports/SDKs, never submit real broker/exchange trades or transfers, and do not validate funded-account execution. Native desktop and real Demo/Testnet/Live execution require separate explicit testing.

The queue first prepares daily history, reusing covered ranges without network requests and downloading only missing daily ranges, then converts it locally. Both daily and weekly CSVs remain available; conversion never removes daily bars or their indicators. Each symbol has a daily preparation job and a weekly conversion job, with normal cancellation/restart recovery. Weekly bars start **Monday at 00:00 UTC**. Open/close use the first/last available daily bar, high/low use their extrema, and volume is summed without decimal rounding drift. Hidden partials, backups, directories, symlinks and removed files do not count. The selected symbols use the normal saved preferences.

**Download** matches existing CSVs by symbol and timeframe, independently of their filename dates, and publishes **one CSV for each symbol/timeframe**. It reuses local history and requests only uncovered parts of the selected From–To interval: an earlier From prepends data, a later To appends data, and gaps between separate saved ranges are fetched only when requested. **Simulate trade**, beside **Add condition**, adds optional **Trade type**, **Stop Loss**, **Bars ago**, **Take profit** and **Duration** controls. Its **Bars ago** defaults to **0**, using the matching bar's value; **1** uses the preceding bar's value. Whole offsets from **0–10,000** are supported, with unavailable earlier values counted as invalid levels. Long uses `TP = entry + multiple × (entry − SL)`; Short uses `TP = entry − multiple × (SL − entry)`. For example, at entry 100, 2xSL gives TP 110 for a Long with SL 95, or TP 90 for a Short with SL 105. Levels remain fixed after entry. Enter a whole **Duration** from **1–10,000 bars**. **Remove simulation** disables it; drafts and named conditions retain the settings across restart, load and rename.

After Apply, each match independently opens a simulated trade of the selected type at the next available closed bar's open. That entry bar is the first duration bar. Long requires `SL < Entry < TP`; Short requires `TP < Entry < SL`, so Stop Loss is above both Entry and Take profit. Existing saved simulations with no direction remain Long. Missing levels or a next-bar opening gap outside that bracket count as invalid levels. Active trades resolve opening gaps before intrabar highs/lows; inclusive SL/TP touches count, with SL first when both are touched within one bar and order is unknown. For both Long and Short trades, the first exit is final: a trade stopped on an earlier bar cannot become profitable when a later bar reaches TP. Matches can overlap. ## Predictions

The fixed **Predictions** tab sits immediately to the right of Screener. It forecasts **Close**, using downloaded Screener CSVs rather than live chart caches. Opening it saves chart viewports and releases live chart subscriptions; returning restores the selected chart tab. It does not count toward the twenty chart-tab limit.

1. Download the desired asset and candle period in **Screener → Downloader**. Use **Refresh data and indicators** first if newer actual data is needed. Predictions does not fetch provider data or modify the CSV.
2. Open **Predictions**. The first visit automatically prepares the selected model and an app-managed inference runtime. Progress shows the current download/setup phase and transferred bytes where available. **Start** stays disabled until both are ready. You can cancel, then explicitly retry; interrupted artifact downloads are retained for resuming. Opening Settings alone does not start a download.
3. Use **Filter assets** to narrow the asset dropdown by name or symbol; matching ignores letter case. Clearing the filter restores all downloaded assets. Filtering preserves the currently selected asset and period. Select an asset and one of its downloaded candle periods (including **w1**), then choose the latest **512 or 1024** fully closed bars. Tick files are excluded. At least that many valid closed rows must exist. The future horizon defaults to **20** and accepts **1–256** bars. These selections are remembered across restarts.
4. Click **Start**. The app reads ordered, finite Close values, excludes the still-open candle, checks the source for concurrent changes and runs the pinned Toto 2.0 model locally on CPU. Model loading and inference status remain visible. Cancel leaves saved snapshots and original CSVs intact.
5. Inspect historical Close, the median forecast and the shaded estimated **10th–90th percentile** band. Series names appear in the legend only, keeping chart labels uncluttered. You can pan and zoom. History retains real UTC timestamps; future bars are numbered **+1** through the requested horizon relative to the last observed closed bar. Future calendar timestamps are not invented, so weekends, session holidays and gaps do not produce misleading dates.
6. Select an earlier **saved forecast** to inspect it again. Each entry shows the model used for that run, alongside its asset, period, creation time and bar counts. Each immutable snapshot retains the input history and model output as they were at that run; refreshing actual data does not rewrite a past forecast.
7. To delete a snapshot, right-click its entry in **Saved forecasts** and click **Remove**. You can also focus the entry and press **Shift+F10** or the context-menu key. Removing the displayed forecast selects the newest remaining snapshot; removing the last clears the chart. The deletion and selection survive restart, and source CSVs, other forecasts and downloaded models are preserved. Finish or cancel active model preparation/inference before removing forecasts. Press **Escape** or click outside to dismiss the menu.

### Model and storage settings

**Settings → Predictions** defaults to **[Datadog/Toto-2.0-313m](https://huggingface.co/Datadog/Toto-2.0-313m)**. The selector also offers the official 4m, 22m, 1B and 2.5B checkpoints. The default 313m weights occupy about **1.2 GB**; larger models require substantially more disk space and memory. CPU inference can take time, especially for larger checkpoints. The app uses the published `toto-2` package and a pinned CPU PyTorch runtime; it does not require a hosted model API, API key, GPU or global Python installation. [Upstream Toto documentation](https://github.com/DataDog/toto) describes the model family and its nine predicted quantiles.

The page shows the default and current **model storage folder**. On Linux the default is `~/.local/share/cryptodesk/predictions/models`; more generally it is `<profile>/predictions/models`, including `data/predictions/models` in the Windows portable profile. Choose another absolute folder and apply it before preparing the model. Changing the folder does not move or delete previous models. Settings cannot change while preparation or inference is active.

The private Python environment and pinned wheel cache live under `<profile>/predictions/runtime`, independently of the chosen model folder. Initial preparation needs internet access to the official Python release, package-wheel hosts and Hugging Face. Model repository revisions, download sizes and SHA-256 checksums are pinned; preparation validates artifacts before marking them ready, and inference rechecks its inputs. No model repository code is executed. Runtime setup and downloads stay within app-owned folders and do not change system packages or shell configuration. Linux and Windows x86-64 are supported.

Forecasts live in **`<profile>/predictions/forecasts`**, separately from Screener market data. JSON snapshots record the UTC creation time and input cutoff, symbol, description, period, lookback, horizon, model ID/revision, source filename and SHA-256, historical Close values and each future step's 10th/50th/90th percentiles. The newest 100 are listed in the interface; older snapshots remain on disk and become visible as newer entries are removed. Snapshots are deleted only through an explicit **Remove** action. `<profile>/predictions.json` stores machine-local settings and selections. Workspace export/import does not include models, prediction preferences or forecast snapshots; back up these folders separately when needed.

Malformed or unordered source timestamps, invalid Close values, insufficient closed history, duplicate CSV ranges for the same asset/period, model download errors and inference errors are reported. For legacy duplicate ranges, use Screener Refresh to consolidate the history before retrying. A changed source during inference prevents publishing a potentially inconsistent snapshot. Failed preparation never falls back to example data. Forecast values are estimates; an 80% model band is not a guarantee that future market prices remain inside it, and this feature does not establish trading profitability or send alerts.

## Trade history

Open **Trade history**, immediately to the right of **Predictions**, to review Dukascopy and Hyperliquid orders submitted through CryptoDesk. The table shows source/account, instrument, native order ID, exchange-confirmed open/close dates, base-unit size, direction, filled **Entry price** and **Exit price**, SL/TP prices, estimated SL/TP amounts, current/final **Profit/Loss** and **Profit/Loss, pips**, balance at submission and position margin when available. **SL/TP amounts use the trade’s account currency**, explicitly labelled EUR, USD, USDC or USDT; they are not converted into dollars. History refresh recovers account currency and a verified conversion for older trades that lack their original preview snapshot. Closed Dukascopy orders may stop reporting protective levels. History retains the last recorded SL/TP, or recovers the original submitted prices if an older refresh erased them. These prices are labelled **Last recorded** or **At submission**; submitted levels are not asserted to be the final exchange settings. Existing closed records recover on load without a login or manual data edits. Live orders still honour removal of SL/TP. Open-trade estimates use the remaining base-unit size; closed-trade risk estimates retain the original filled size. They use the actual filled entry, direction and SL/TP levels, before fees. Missing conversions remain explicit rather than assuming EUR and USD are interchangeable. A genuine zero balance is displayed as zero; unavailable values display **—**.

**Exit price**, immediately after Entry price, is the quantity-weighted average of confirmed closing fills after the whole trade closes. It includes all partial exits, rather than just the final closing price. Open/partially open positions and incomplete closing histories show **—**. Existing saved records recover the new fields during exchange refresh when complete provider history remains available.

**Profit/Loss, pips**, immediately after the monetary Profit/Loss column, uses the [Dukascopy SDK’s native instrument pip P/L](https://www.dukascopy.com/client/javadoc3/com/dukascopy/api/IOrder.html#getProfitLossInPips--), rounded by the broker to 0.1 pip and labelled **pips**. It is independent of account-currency conversion. For Hyperliquid, the column explicitly labels values **ticks**, as selected by the user: one tick is the valid price increment at the filled entry, fixed for that trade using the [exchange’s significant-figure and asset-decimal rules](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/tick-and-lot-size). Tick P/L combines quantity-weighted realized price movement with the remaining position’s unrealized P/L, normalized by the original filled size and entry tick; it excludes fees/funding. A rise benefits Long and a fall benefits Short. Hover a value for its basis and unit size. Current pip/tick values expire when status refresh stalls; confirmed closed values persist across restart. Missing values, incomplete histories and mixed Hyperliquid exposure remain **—**, while a confirmed zero displays **0 pips** or **0 ticks**.

**Profit/Loss** shows the broker/exchange-reported value in its labelled currency, with **Current** or **Closed** beneath it. Dukascopy reads its native account-currency position P/L; Hyperliquid combines attributable realized fill P/L with current unrealized position P/L, excluding fees/funding. Confirmed final results persist across restart. Current values expire if status refresh stalls; mixed Hyperliquid exposure, missing provider fields and non-position spot executions remain unavailable. Hover the amount for its basis or the unavailable reason. The refresh notice occupies reserved space above the table, so polling does not shift the table. Healthy order-verification details are kept out of the Status cells.

The list comes only from this profile’s durable order-submission journals. Exchange APIs update these recorded orders; orders placed elsewhere are never imported. Records survive restart and credential changes, but status/Close requires the original account and environment. Older submissions can be recovered using their recorded client ID/label. Current risk conversion and native P/L can be retrieved on refresh; historical balances and execution details outside the client’s retained history cannot be reconstructed. Keep the profile’s `hyperliquid-orders` and `dukascopy-trade-claims` folders with your data backups. Opening this screen reads saved rows immediately, then checks the displayed page against the exchange; active positions refresh every 20 seconds while the screen is visible. No history request runs merely because the app starts.

Select an open row and press **Close**, review the account, order and remaining size, then choose **Confirm market close**. Cancelling the review does not trade. Dukascopy uses the SDK’s exact-position `close()` operation and verifies both its native order ID and CryptoDesk label. Use this build’s matching app/bridge bundle and restart after upgrading. Its SDK does not expose reliable per-position margin, so that column remains unavailable rather than showing account-wide margin. See the official [JForex order API](https://www.dukascopy.com/client/javadoc3/com/dukascopy/api/IOrder.html).

Hyperliquid uses a reduce-only IOC market exit with a 1% slippage cap; a partial fill leaves a remaining quantity that can be reviewed again once reconciled. Close is enabled only when the exchange fill history proves that the remaining net exposure belongs to this platform trade. Other trades that increase the same position, incomplete provider history or an uncertain previous close disable individual Close. Spot executions are shown, but are not separately closeable positions. Only this trade’s own protective client IDs are cancelled after a full manual exit; any unconfirmed cancellation is reported. The [Hyperliquid history API](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint) exposes limited fill history, so older positions can remain unverifiable. An exchange-confirmed closure supplies the close date; pending/uncertain responses never invent one or automatically resend a close.

## Save, export and recover

Workspace data lives at `$XDG_DATA_HOME/cryptodesk/workspace.sqlite`, normally `~/.local/share/cryptodesk/workspace.sqlite`, with user-only permissions. A local lock prevents another process from editing the same store. For an isolated profile use `./cryptodesk --data-dir /absolute/test-directory`.

Autosave uses 500 ms idle debounce with at most two seconds of deferral, ordered edit sequences and acknowledged SQLite revisions. Tab switches flush; native close captures viewports and awaits the final commit. When launched from a terminal, **Ctrl+C** follows that same save-and-close flow; **SIGTERM** also requests a graceful close. Closing during startup cancels initialization safely before an interactive draft exists; later interrupts follow the ordinary final-save handshake. A save failure keeps the app open with retry/discard options; repeated interrupts do not discard unsaved changes. A forced kill can lose pending frontend edits; the last acknowledged commit survives.

Import/export uses native JSON file dialogs. Imports are limited to 5 MiB, strictly validated, previewed, confirmed and transactionally replace the workspace with a consistent backup. Exports contain configuration only. At most five recovery snapshots are kept in the workspace database. Reset is explicit and confirmed. Invalid/future saved documents are preserved and open a recovery screen, with backup/import/reset choices. A physically unreadable database fails startup with an error and preserves the file.

For a portable backup, export JSON. To copy the database manually, close the app first and retain any `-wal`/`-shm` companion files; do not copy only a live main database file. Move a corrupt database and its companion files aside before an explicit fresh profile; never delete them as an automatic recovery shortcut.

## Boundaries and attribution

Memory caches, history request sizes, queues and rendered instances are bounded. The optional disk candle cache is persistent and can grow; it has no automatic deletion. Active series retain at most 10,000 bars in a moving window: older-history loads evict newer bars while preserving the selected historical range, and Return to live reloads the latest window. Full manual desktop, high-DPI and target-release coverage is recorded separately in STATUS.md; automated browser tests do not establish those checks. Exact window position on Wayland is best effort; normal size and maximized state are saved.
