GitHub's current [workflow syntax documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency) explicitly supports `queue: max`, which queues up to 100 waiting runs. GitHub also documents that [waiting order can differ from dispatch order](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency); ancestor and workflow-content checks protect latest downloads when an older event starts later.

GitHub's [release API documentation](https://docs.github.com/en/rest/releases/releases) describes the additional Workflows permission restriction when releasing commits whose workflow files differ from the current default branch. `GITHUB_TOKEN` cannot gain that permission. The planner reads the actual remote `main` ref through the API and skips older workflow contents; a second check prevents writes if the workflow changes during a build. The newer push releases the accumulated changes. Reading the API matters because the [pinned checkout implementation](https://github.com/actions/checkout/blob/d23441a48e516b6c34aea4fa41551a30e30af803/src/git-source-provider.ts) can reset local `origin/main` to an older event SHA.
